Why everything is a file

Read this to understand the design bets behind the plugin. Decisions live in committed files instead of chat memory, commands only ever add to those files, and the shape of a command's arguments carries the meaning that flags would otherwise carry.

Decisions live in files, not in the conversation

A chat session is a bad place to store a decision. The session ends, the session compacts, and the summary loses detail. The next session then starts cold, with no record of the decision. The plugin's answer is strict: nothing that matters may exist only in conversation. Every stage of a workflow writes a numbered Markdown artifact into .ai/workflows/<slug>/.

These artifacts include the intake interview, the shaped scope, the slice breakdown, the plans, the verification evidence, and the review findings. When the product owner answers a question, the answer lands in po-answers.md. When you want to give standing instructions to every future stage, write the instructions in steer.md.

The payoff is that any session can pick up a workflow cold: your session tomorrow, a teammate's session, or an autonomous driver's session. Nobody needs to explain the history again, because each stage reads each decision from the artifact that recorded the decision. /wf recap exists because the files are the memory. The command reads the files back to you in plain language.

Numbered artifacts are the contract between stages

The numbers are not decoration. 01-intake.md feeds 02-shape.md, which feeds 03-slice.md, and so on through verify, review, handoff, and ship. Each stage declares which upstream artifacts it consumes, and each stage refuses to run meaningfully without them. Handoff, for example, checks that an implementation artifact exists for every slice in scope before it packages anything.

The contract is a set of files with known names and known frontmatter. Every artifact carries schema: sdlc/v1, a type, and a slug that matches its directory. Because the contract is mechanical, a hook can validate a write before the write happens, and the plugin can build the rendered workflow view from the same files. The 00-index.md control file at the top of each workflow holds the durable cross-cutting state: the charter, the risk ledgers, and the branch configuration. Every stage reads this state, and only specific stages may update it.

Ledgers are additive-only

Commands never overwrite or delete artifacts. When you re-run a stage, the stage appends a new revision to the same file. When you close a workflow, /wf close archives the workflow with 99-close.md. The command never deletes files, branches, or PRs.

The record-keeping structures that grow over time follow the same rule with more force. These structures include the review ledger, the intent-risk ledger, the runtime-evidence deferrals, and the ship-plan audit. Re-runs merge and dedupe entries, keep the IDs and timestamps of existing entries, and mark cleared findings resolved instead of erasing them. A finding that was raised once stays visible forever, together with its outcome.

This rule is what makes the files trustworthy as a record. If commands could rewrite history, the artifacts would only tell you the current story. Because commands cannot rewrite history, the artifacts tell you the whole story, including the parts where the first answer was wrong.

Reviewers route findings; they never write code

The plugin draws a hard line between commands that observe and commands that change things. /wf review, /wf simplify, /wf probe, /wf status, and the audit modes of ship-plan and observability are all orchestrators. Each one investigates, classifies what it finds, and routes each finding to the command that may fix it. That command is usually /wf implement <slug> <slice> reviews. The orchestrators do not patch code themselves, even when the fix looks small.

The reason is accountability. A reviewer that fixes as it goes produces changes that no stage planned, verified, or recorded. A reviewer that only routes produces a ledger entry that an accountable stage must consume. The same discipline applies inside the machinery: the external oracles behind /consult can read the repository, but they cannot write to it.

Convention over flags

No /wf command takes a --flag. The shape of the arguments is the signal. A first token that matches an existing workflow slug means you address that workflow. A bare mode keyword means you start something standalone. An existing slug followed by free text means extension: intake reads "slug plus new scope" as a request to add full new slices to that workflow, with no keyword required.

The intake reference states this directly: the scope is the signal. Intake resolves the arguments in a fixed order:

  • a maintenance keyword,
  • then a quick-lane mode,
  • then an extension,
  • then a standalone mode,
  • then a plain description.

Because the order is deterministic, the same words always mean the same thing.

The bet is that a small set of positional conventions, applied everywhere, is easier to hold in your head than a large set of per-command options. Where a convention could surprise you, the command states what it inferred before it acts. Intake confirms a suggested mode instead of routing silently, and a quoted description forces the default path.

The External Output Boundary

Everything above describes a rich private record, and that record must stay private. The plugin's most repeated rule is the External Output Boundary. Everything under .ai/ or .claude/ is internal implementation context. The workflow vocabulary is also internal: stage names, command names, and artifact paths. Commit messages, branch names, PR titles and bodies, release notes, changelogs, code comments, and user documentation are external. Internal context never crosses into external text.

The rule is "translate, do not cite". When a stage produces a PR body or an announcement, the stage restates the workflow context in product language: what changed for users, why it changed, how it was verified, and what the risks are. The external text never mentions that an SDLC workflow produced it, and the external text never points at private artifact files. Every stage performs a leak check before it publishes anything, and an optional hook can guard commits and PR text mechanically.

There is one sanctioned exception: the chat summary at the end of a command run. You are an internal audience, so .ai/ paths may appear there. The boundary governs what leaves the session, not what you see inside the session.
