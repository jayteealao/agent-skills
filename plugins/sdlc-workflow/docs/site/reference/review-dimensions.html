Review dimensions

This page lists the 11 review rubrics, the 24 alias names that keep every former dimension reachable, the 7 sweep aggregates that bundle the rubrics, and the rules for ad-hoc invocation. Use this page to pick the right rubric for the review you want.

Commands on this site are written as /wf …. Under Codex, type $wf … instead. The key and the arguments are the same.

Invocation and scope

Review has two modes, and the first token tells them apart. /wf review <slug> is the workflow stage: it dispatches one reviewer per selected rubric and merges findings into the accumulating ledger (07-review[-<slice>].md plus one file per rubric). Without a slug, /wf review <rubric> runs one rubric inline, /wf review <alias> runs one section of a rubric, and /wf review sweep <aggregate> fans out one reviewer per bundled rubric. These slug-less runs are the ad-hoc path. Ad-hoc runs write no artifact. Findings return inline in chat, with a verdict and severity counts.

Ad-hoc review runs over one of five scopes, parsed from the remaining tokens:

ScopeTarget
pra PR URL or number
worktreethe uncommitted working-tree changes
diffa commit range
filea file path
repothe whole repository (also the bare default)

To reach a rubric whose name is also a real workflow slug, invoke /wf review sweep <name>, or run the rubric in a repo without that slug.

When a rubric name is also a real workflow slug, the slug wins and the stage runs.

The 11 rubrics

Each rubric is one file of at most 100 lines that the reviewer follows. A rubric has four parts: a role, a What to look for list with one section per alias, a shared severity calibration, and the output shape. Each entry below describes one rubric and names its sections:

correctness
Reviews logic flaws, broken invariants, edge cases, test quality, data integrity, concurrency, and reliability under failure. Sections: correctness, testing, data-integrity, backend-concurrency, reliability.
security
Reviews code, infrastructure, dependencies, and data handling for vulnerabilities, insecure defaults, supply-chain risk, and privacy exposure. Sections: security, infra-security, supply-chain, privacy.
performance
Reviews algorithmic and system performance, frontend rendering and bundle cost, behavior at scale, and cloud spend. Sections: performance, frontend-performance, scalability, cost.
architecture
Reviews structure and simplicity: boundaries and dependencies, maintainability, overengineering, missed reuse, style consistency, and refactor safety. Sections: architecture, maintainability, overengineering, code-simplification, style-consistency, refactor-safety.
api-contracts
Reviews API contracts and database migrations for stability, compatibility, and safe operation in production. Sections: api-contracts, migrations.
accessibility
Reviews UI changes for keyboard and assistive-technology usability, ARIA correctness, and SPA-specific accessibility. Sections: accessibility, frontend-accessibility.
interface-craft
Reviews the static visual detail and the motion that make an interface feel polished: radii, alignment, shadows, tabular numbers, hit areas, easing, timing, interruptibility. Sections: interface-craft, motion.
docs
Reviews documentation completeness and Diátaxis fit, user-facing copy, and controlled-language compliance of text at rest. Sections: docs, ux-copy, ste-compliance.
observability
Reviews observability and logging: wide events, metrics, tracing, error reporting, alertability, runbook hooks, and secrets or PII in logs. Sections: observability, logging.
infra
Reviews infrastructure, CI/CD pipelines, release safety, and developer tooling for safety, least privilege, and operational clarity. Sections: infra, ci, release, dx.
intent-fidelity
Reviews whether the diff advances the intake's product or a simplified imitation of it. This code-to-intake fidelity is the thing every other rubric misses. Section: intent-fidelity.

The 24 aliases

Every former dimension name stays a valid key. An alias resolves to its rubric with a focus: the reviewer reads that one section plus the severity calibration, so /wf review logging stays as narrow as it was. The 7 sweep aggregates

A sweep dispatches one reviewer sub-agent per bundled rubric, in parallel. The sweep then dedupes the findings and synthesizes them into a single verdict. Invoke a sweep with /wf review sweep <aggregate>:

AggregateRubrics bundled
allevery rubric (11 reviewers — the broadest and most expensive)
architecturearchitecture, performance, api-contracts
infrainfra, observability, api-contracts
pre-mergecorrectness, security, architecture
quickcorrectness, architecture, docs
securitythe security rubric with all four sections (one reviewer)
uxaccessibility, interface-craft, docs, performance (focus frontend-performance)

Bare name vs sweep. Three names exist as both a rubric and an aggregate: architecture, infra, and security. A bare /wf review architecture runs the single rubric. /wf review sweep architecture runs the three-reviewer aggregate. The same rule holds for the other two names.

What gets written

Remember one distinction. Ad-hoc runs (a rubric, an alias, or a sweep, with no slug) write no artifact. Their findings, severity counts, and verdict return inline, and they are gone when the chat is gone. Stage runs (/wf review <slug>) write the accumulating review ledger. Re-runs merge and dedupe in place, preserve finding IDs and surfaced-at stamps, and mark findings that a re-run no longer surfaces as resolved. Nothing is ever overwritten or deleted.
