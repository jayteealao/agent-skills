Glossary

This page defines every term of art the plugin uses, alphabetically and in plain language, and maps older internal names to their current ones. Come here when a command or artifact says "wall-ownership" or "clears-on" and you want the one-paragraph version.

acceptance criterion (AC)
One testable statement of what the finished work must do, written at shape and numbered. Verify gates on the ACs: each AC must be proven met, recorded as failed, or explicitly deferred. No AC is ever silently skipped.
accumulating ledger
A file that only grows. A re-run of the command that owns the ledger merges new entries in, deduplicates against prior entries, and marks cleared entries resolved. A re-run never overwrites or deletes. The review artifact and the ship-plan audit are the main examples.
add-on (formerly "augmentation")
Optional extra work a workflow can carry alongside its slices: telemetry instrumentation, an experiment, a benchmark. Add-ons are decided at shape, recorded in the augmentations: frontmatter block, and materialized as the 04b/04c/05c artifacts.
adjudicated / carried / open
The three states of an intent-risk entry. An entry starts open at intake. Shape either resolves the entry with the product owner (adjudicated) or deliberately carries the entry forward as a known risk (carried). Handoff and ship refuse to run while any entry is still open.
aggregate / sweep
A named bundle of review dimensions run together (all, pre-merge, security, ux, and so on), invoked as /wf review sweep <aggregate>. This is distinct from a probe sweep, which drives the running app; see surface-defect taxonomy.
appetite
How much the work is worth to you: small, medium, or large. You answer once at intake, and the answer is recorded in the control file. Later stages read the appetite to calibrate how many slices to expect, how far pre-mortems look, and when to seek a second opinion.
charter
The 3–7 positive commitments the build must honor, distilled from your request at intake and ratified by you before they are written. Each commitment must be falsifiable by code. The commitments live in 00-index.md and outlast any single slice. Review and probe check work against them.
charter scenario
The executable end-to-end spine of the feature: the numbered "user does A, gets B, then C" loop restated at intake. Shape turns the loop into the one scenario that must demonstrably run.
clearing event
The named act that resolves a runtime-evidence deferral. A clearing event is always something an actor does ("provision the staging device", "merge the credentials PR"), never a passive wait. Every deferral must carry one.
clearing probe / tripwire
A one-line, side-effect-free command that answers whether the clearing event happened yet, for example curl -sf localhost:8080/health. Status, probe, and the drivers execute clearing probes opportunistically and flag hits. A clearing probe is a tripwire, not a gate: it tells you that evidence can now be collected, and it never clears anything by itself.
compressed slice
The file-format name for a quick-lane slice: the single slice a fix/hotfix/refactor/update-deps entry (or probe/simplify) attaches to a workflow. The slice is authored in one run rather than through the full slice stage.
decidability
The boundary probe respects between what watching a running app can prove and what it cannot prove. A visible defect is decidable by observation. An absence property ("there is no injection here") is not decidable, and is routed to review instead of being claimed from a probe run.
decisionDigest
The structured summary an autonomous driver returns of every decision it made on your behalf. The intent-bearing decisions are called out as stop-worthy escapes for you to inspect.
dimension
One reviewer specialty: correctness, security, performance, intent-fidelity, and about thirty more. A review run selects dimensions, fans each dimension out to its own sub-agent, and merges the findings into the ledger. See Review dimensions.
Documentation Plan
The section of the shape artifact that decides, up front, what documentation this work owes and in which Diátaxis form. /wf docs in workflow mode exists to fulfill the Documentation Plan.
drift finding / clears-on
A drift finding is a detected mismatch between the ship plan and what the repo or branch actually does. Each finding is tagged clears-on: amend | repo | merge, the event that genuinely resolves the finding. The tag makes an acknowledgement or amendment clear exactly the findings it should, and no others.
driver
A command that runs other stages for you instead of doing stage work itself. /wf auto pauses at every gate for you. /wf yolo resolves gates autonomously by a written policy. Both drivers stop before handoff.
driver journal
The append-only heartbeat file (.driver-journal.jsonl) an autonomous driver writes as it works. A stalled or interrupted run can be diagnosed and resumed from the record rather than from memory.
environment-class
Where a probe's evidence actually came from: production, staging, local-emulated, or mocked. The class is recorded in the probe artifact, so nobody mistakes evidence from a mock for evidence from the real thing.
evidence ladder / env-remediation rung
The ordered set of ways to produce runtime evidence, from cheapest to most real. The env-remediation rung is the step people skip: before you declare the environment unusable, try to fix the environment (boot the emulator, start the service). Only after the ladder is exhausted may an AC become a deferral.
External Output Boundary
The rule that anything leaving the repo (PR bodies, commit messages, announcements) speaks product language. Outward text never mentions .ai/ paths, slugs, or other internal workflow machinery.
fingerprint-scope
What a ship-plan acknowledgement is a claim about. plan-scoped entries die when the plan version bumps; an amended plan must re-earn them. branch-scoped entries assert a fact about the branch, survive amendments, and die at merge.
gate
Any point where a stage stops and requires something before the stage proceeds: a product-owner answer, passing checks, a clean readiness check. Gates belong to the stages themselves. The drivers differ only in who answers the gates.
hub
The one machine-wide background service (a local Node daemon on 127.0.0.1:4173). The hub serves every registered repo's workflow view, the code browser, and this documentation, and drains the render queue. The hub starts automatically at session start.
implementation-detail vs intent-bearing decision
The two classes of decision an autonomous run can make. Implementation-detail choices (variable names, an internal helper's shape) are safely made alone. Intent-bearing choices change what the product does or means, and a driver must surface them to you rather than absorb them.
intent-risk (RIM) ledger
The intent-risks: block in the control file: an explicit list of the ways your request could plausibly be misunderstood. The list is written at intake and adjudicated with you at shape. Its job is to make misreadings a tracked object instead of a silent drift. RIM stands for "risk-if-misunderstood".
narrative fragment
A free-form HTML file (<stem>.<NN-label>.html.fragment) placed next to any artifact to add a custom diagram or widget to the artifact's rendered page. The fragment is unrestricted raw HTML, injected below the page body in label order.
perturbation
Probe's controlled break: disable exactly one dependency, observe how the app behaves, restore the dependency. Perturbation is how dependency-collapse and branch-gap defects are found on purpose rather than by luck. It is never done to a shared or production backend without authorization.
PO (product owner)
You. The stages interview the PO, gate on PO decisions, and log every answer in po-answers.md. The plugin never invents a PO answer.
quick lane
The shortened path for small, well-understood work: the fix, hotfix, refactor, and update-deps intake modes. These modes author stages 1–4 in a single run and stop at the pre-implement gate. Formerly called the "compressed flow".
quick-lane slice
See compressed slice: the single-slice attachment a quick-lane entry (or probe/simplify) adds to a workflow.
readiness check
The pre-flight that handoff and ship run before they act. It asks: is the ship plan present and current, is CI green, is the tree clean, are the ledgers clear? Formerly called the "readiness gate" or "readiness verdict".
registry
Two files answer to this name. The workflow registry is .ai/workflows/INDEX.md: one tab-separated row per workflow, reconciled by every /wf status run. The workflow registry is what lets commands recognize a bare slug. The hub registry (~/.sdlc/registry.json) is the machine-wide list of repos the hub serves.
render queue
The durable on-disk queue (.ai/_view/.render-queue/) that artifact writes enqueue render jobs into. The hub daemon drains the queue, so views stay current without any command blocking on rendering.
review scope
Whether review keeps one ledger per slice (per-slice) or one ledger for the whole workflow (slug-wide). The scope is recorded in the control file and confirmed with you once at the slice stage, when the slice count is known.
router
The old internal name for what the documentation now simply calls the command: /wf reads its first argument and dispatches to the matching reference. If you see "skill router" in older material, read it as "the /wf command".
run-id
The identifier of one release attempt. Each /wf ship run gets a run-id, names its 09-ship-run-<run-id>.md record with the run-id, and can be replayed or rolled back by the run-id.
runtime-evidence deferral
A recorded, ship-blocking IOU: an acceptance criterion whose runtime proof could not be produced yet. A deferral requires a wall-ownership verdict, a named clearing event, and (strongly expected) a clearing probe. Ship refuses to run while a deferral is open. A deferral means "evidence missing". A criterion that was driven and found broken is a fail, never a deferral.
sdlc-debt marker
A structured sdlc-debt: comment left in code where a deliberate shortcut was taken. /wf simplify harvests the markers repo-wide, so the debt is findable instead of folkloric.
slice
One thin, independently verifiable vertical piece of a work item. A slice is small enough to plan, build, and prove on its own, end to end. The slice stage decomposes a shaped feature into slices.
slice-slug
The short identifier of one slice within a workflow. It appears in filenames (04-plan-<slice-slug>.md) and as the positional argument to plan, implement, verify, and review.
slug
The short kebab-case name of a whole workflow: the directory name under .ai/workflows/, the frontmatter slug: field, and the argument every command takes. The slug is chosen at intake and never changes.
stack fingerprint
The stack: block intake detects and asks you to confirm: platforms, languages, UI toolkit, build tools, testing tools, observability, integrations. Downstream stages base tooling decisions on the fingerprint and treat an unconfirmed fingerprint as advisory.
steering (steer.md)
Your standing instructions for a workflow, kept in steer.md in the workflow's directory. Every stage, and every sub-agent a stage dispatches, reads and honors them. Steering shapes work beneath the gates but never overrides a mandatory gate.
sunflower
The internal code name for the workflow view: the rendered dashboard the hub serves from .ai/_view/. If you see "sunflower" in source or older notes, read it as the dashboard.
surface-coverage / enumeration method
The record, in a probe sweep, of how the artifact's surfaces were enumerated (screens, routes, commands). The record lets a reader tell what the sweep actually covered and what the sweep never visited, rather than assume that "swept" means "everything".
surface-defect taxonomy
The eight classes of defect a probe sweep looks for at the running surface: dead-affordance, error-surface-leak, terminal-wait, fabricated-value, dependency-collapse, branch-gap, boundary-overflow, and env-interference. The taxonomy needs no domain knowledge. Anything domain-specific comes from the charter instead.
verdict
Review's bottom line for the scope it examined: ship, ship-with-caveats, or dont-ship. Handoff aggregates verdicts across slices.
wall
Anything that stops evidence from being produced or work from proceeding: a missing device, an unprovisioned credential, a hard-coded port. To name the wall precisely is the first step. To triage who owns the wall is the second step.
wall-ownership
The mandatory triage of a wall before the wall may justify a deferral: code-owned (the code itself causes the wall; it must be fixed, never deferred), environment-negotiable (the environment could be fixed from here), or external (genuinely outside the team's reach).
workflow view
The rendered HTML dashboard of a repo's workflows, generated into .ai/_view/ by the render pipeline and served by the hub. The view is read-only: it is regenerated from the artifacts and never hand-edited.
