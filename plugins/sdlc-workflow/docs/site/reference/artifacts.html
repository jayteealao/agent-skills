Artifact files

This page maps every file that /wf writes into a repository. Use it to identify a file in .ai/, find the command that wrote the file, and learn whether you can touch the file.

The plugin writes to three places: the per-workflow directory .ai/workflows/<slug>/, some project-level files directly under .ai/, and three optional context files at the repo root. Artifacts are plain Markdown files with YAML frontmatter. Artifacts are the record of the work. Commands treat artifacts as additive: a command never overwrites or deletes an artifact.

The workflow directory: .ai/workflows/<slug>/

Each workflow gets one directory, named by the workflow's slug. Files inside the directory follow a numbered convention: a two-digit stage prefix, an optional letter for a stage add-on, then a hyphenated name (for example 01-intake.md, 02b-design.md, 04-plan-api.md). A blocking write hook enforces the convention, so a stray filename never lands. The numbers run in lifecycle order:

A few files in the directory deliberately sit outside the numbered convention:

  • po-answers.md — the cumulative product-owner decision log. It is free-form prose with no frontmatter. Every stage appends the questions it asked and the answers it received.
  • steer.md — your standing instructions for this workflow. You own this file. Stages read it and never write it.
  • skip-slice-<slice>.md — written by /wf close when you close a single slice rather than the whole workflow.
  • design-notes/ — per-run artifacts from /wf design transformation commands and read-only extraction (for example extract.md, animate-<ts>.md). These files are named by operation, not by stage number.

The control file: 00-index.md

The control file is almost all frontmatter. It has no meaningful Markdown body. Every stage reads the control file on entry and updates it on exit. The basic identity and progress fields are title, status, current-stage, branch, and a per-stage progress: map. Beyond those, some frontmatter blocks carry durable state that later stages and the drivers depend on:

workflow-type:
The discriminator that tells every downstream command what kind of workflow this is: standard, fix, hotfix, refactor, update-deps, rca, investigate, discover, task, audit, and so on. Routing and stage behavior key off this field.
review-scope:
Either per-slice or slug-wide. This field decides whether review writes one ledger per slice or one ledger for the whole workflow. Intake records a provisional default. The slice stage confirms the value with you when the slice count is known (review-scope-confirmed: flips to true). Handoff gating also reads this field.
the slice roster (slices:)
One entry per slice with the slice's status, complexity, and dependencies. Drivers and /wf status use the roster to tell a finished slice from a live or skipped one.
charter:
The 3–7 positive commitments the build must honor. Intake distills the commitments and you ratify them (entries carry po-ratified: true). Each commitment must be falsifiable by code. When a workflow genuinely has no commitments, the control file records charter: none-declared plus a one-line reason. Silence is not allowed. Review's intent-fidelity dimension and /wf probe sweep read the charter as a comparison basis.
intent-risks:
The intent-risk (RIM) ledger: the ways the request could plausibly be misread. Intake writes each entry as open. Shape adjudicates each entry: the entry becomes adjudicated or carried. While any entry is still open, handoff and ship hard-block. An empty ledger must be declared explicitly, like the charter (intent-risks: none-declared).
runtime-evidence-deferrals:
The ship-blocking IOU list: acceptance criteria whose runtime proof could not be produced at verify time. Each entry records the reason, a wall-ownership triage verdict, a clearing-event, and a clearing-probe. A code-owned wall may not be deferred at all. The clearing event names the act that clears the entry. The clearing probe is a side-effect-free command that /wf status, probe, and the drivers run as a tripwire. While any entry has cleared-by: null, /wf ship refuses to start.
augmentations:
The add-on plan decided at shape: which of instrument, experiment, and benchmark this workflow carries. This field is what makes the 04b/04c/05c files appear later, or not appear.
stack:
The stack fingerprint intake detected (platforms, languages, UI toolkit, build, testing, observability). The user-confirmed: field records whether you signed off on the fingerprint. Downstream stages treat an unconfirmed fingerprint as advisory only.

The registry: .ai/workflows/INDEX.md

One file above the workflow directories indexes them all. The file is one header comment line followed by one tab-separated row per workflow, sorted alphabetically by slug:

<slug>	<status>	<workflow-type>	<branch>	<updated-at>

Each column comes from that workflow's 00-index.md frontmatter. status is the lifecycle state (defined, shaped, implementing, shipped, closed, and so on). workflow-type is the discriminator described above. branch is informational. updated-at is ISO 8601 UTC. Every /wf status run reconciles the registry against the directories on disk before it does anything else. Closed workflows stay listed. The registry is what lets commands recognize a bare slug argument, so a missing or stale row degrades slug detection. To heal the registry, run /wf status once.

Root-level context files

Three files can live at the repo root, outside .ai/. PRODUCT.md and DESIGN.md are the product and design context. /wf design setup and teach author them, and the lifecycle stages read them. AGENTS.md carries a fenced block of /wf ground rules. A session-start hook seeds and maintains the fenced block, with a matching @AGENTS.md import in CLAUDE.md. The hook owns only its fence. The rest of the file is yours.

The frontmatter contract

Every workflow artifact must open with YAML frontmatter that carries at minimum three fields. A PreToolUse hook blocks any write that violates them:

  • schema: sdlc/v1. The value must be exactly this.
  • type: — the artifact type (index, intake, shape, plan, review, ship-run, and so on).
  • slug: — the value must equal the workflow directory name, and it stays stable for the life of the workflow.

The same hook enforces the numbered-filename convention. The exemptions are deliberate and few: po-answers.md (a frontmatter-less prose log), files under probe-evidence/ (free-form evidence), and design-notes/ (operation-named files that carry the design add-on type instead). All machine-readable state belongs in frontmatter. The Markdown body is for human narrative.

Sibling YAML and fragments

Rich artifact types must ship a sibling <stem>.yaml file next to the Markdown file. The rich types are review, plan, design, ship-run, rca, simplify-run, benchmark, experiment, instrument, and the design audit/critique/contract family. The sibling file holds the structured data that the rendered workflow view builds its figures and tables from. A PostToolUse hook hard-blocks a rich artifact written without a sibling file. A rich artifact with genuinely no structured data may opt out. To opt out, declare fragment: none in the artifact's frontmatter.

Two kinds of HTML fragment can also sit beside an artifact. The typed fragment (<stem>.html.fragment) is the contract-bound interactive layer projected from the sibling YAML. An artifact can carry at most one typed fragment, and only rich types can carry one. A typed fragment is one scoped <section> with inline assets only. Free narrative fragments (<stem>.<NN-label>.html.fragment) are unrestricted raw HTML, injected below the rendered page body in label order. Any artifact can carry any number of them. Use a free narrative fragment for a bespoke diagram or widget that the structured page cannot tell. The NN- prefix on the label controls the order.

Ledger discipline: additive only

Several files are ledgers, and a ledger only grows. The review ledger (07-review[-<slice>].md + its sibling YAML) is the strictest case. A re-run merges: new findings are deduplicated and appended, and prior finding IDs and surfaced-at stamps are preserved. A finding that a re-run no longer surfaces is marked resolved, not removed. Nothing is ever overwritten or deleted. The sibling YAML mirrors the open findings for the rendered view.

The ship-plan acks ledger (.ai/ship-plan-acks.yaml) records the drift findings you acknowledged, so the same settled question is not asked again. Each entry is scoped. Entries with fingerprint-scope: plan are claims about the plan, and they die when the plan version bumps. Entries with fingerprint-scope: branch are facts about the branch: they survive amendments and die only when the branch merges. Each finding also carries a clears-on tag (amend, repo, or merge) that names the event that actually resolves the finding. The intent-risk ledger and the runtime-evidence deferral list in 00-index.md follow the same rule: entries change state (open to adjudicated, cleared-by set), but entries are never erased.

Whether .ai/ is committed or gitignored is a per-project policy, recorded as artifactTracking in .ai/sdlc-config.json. Ship's clean-tree check reads the policy. While the policy is unset, /wf status nudges you once.
