Intake modes

This page lists the fourteen ways work can enter the lifecycle through /wf intake: each mode, how the arguments resolve, what each mode authors, its branch convention, and where each mode ends.

Commands on this site are written as /wf …. Under Codex, type $wf … instead. The key and the arguments are the same.

How the arguments resolve

Intake resolves its tokens in a fixed order, and the order is user-visible. The same words mean different things when the first token names an existing workflow. The checks run in exactly this sequence:

  1. Existing slug + amend or modernize → maintenance. The two maintenance modes are claimed first. Otherwise amend would read as free scope text and modernize would read as a bare keyword. Without a real slug, both modes stop with an error; neither mode means anything standalone.
  2. Existing slug + a mode keyword → compressed slice. The run attaches as one compressed slice on that workflow. The slice file is the sole output, branch creation is suppressed, and no companion directories are written. adopt is the exception: adopt can never attach to a slug and stops here. For a closed workflow, intake asks "append a compressed slice anyway?" before it proceeds.
  3. Existing slug + free text (or nothing) → extension. No keyword is needed: an existing slug followed by new scope is the signal. The run adds full net-new slices to that workflow (see extension below). While intake reads the index, intake also notes whether the workflow predates the current schema. If the workflow predates the current schema, intake offers modernize as a first-class option before it extends.
  4. Bare mode keyword → standalone. The mode runs on its own and creates whatever workflow the mode defines. This matches the natural reading of a description that begins with a mode word ("fix the typo…").
  5. Anything else → the default flow. One twist applies: when the description strongly matches exactly one mode pattern, intake proposes that mode one time and asks. For example, a regression with an unknown cause reads as rca, and a dependency bump reads as update-deps. If you accept, the mode runs standalone. If you decline, the default flow runs. adopt, amend, and modernize are never auto-proposed.

To force the default flow when your description legitimately begins with a slug or a mode word, quote the description as one token: /wf intake "rca dashboard refresh" never matches a slug or a keyword.

An empty invocation renders the mode menu and asks.

The modes

default

/wf intake <description>

The default flow is the canonical stage 1 of 10 and the only mode with no keyword of its own. It converts a rough request into a clear intake brief through a product-owner interview. It fingerprints the stack, establishes the canonical slug, and creates the workflow. The default flow is always standalone; it is never slug-attached.

Authors: 00-index.md + 01-intake.md. Terminus: recommends /wf shape <slug>.

fix

/wf intake fix <description>
/wf intake <slug> fix <description>

fix is the quick lane for small, intentional changes with an obvious correction. Standalone, it authors the entire planning half of a standard lifecycle in one run: intake, shape, slice, and plan on a full overview index. It then stops at the pre-implement gate. The standard chain takes over from there, with the same quality gates as any other workflow. When the run is slug-attached, it becomes one compressed slice on the named workflow.

Authors: 01-fix.md → 02-shape.md → 03-slice.md → 04-plan.md. Branch: fix/<slug> (suppressed when slug-attached). Terminus: gates, then /wf implement <slug>.

hotfix

/wf intake hotfix <description>
/wf intake <slug> hotfix <description>

hotfix is the incident-response quick lane for active production emergencies. It has the same single-pass planning shape as fix, plus a hard scope lock, a diagnosis-oriented shape, and a base on the production branch. Its review stage defaults to the security dimension. The incident brief carries up to two acceptance criteria, so verify and review have something real to gate on, and the pipeline runs the full tail — handoff, ship, and retro (retro's incident consult fires exactly for hotfixes). When the run is slug-attached, it becomes one compressed slice on the named workflow.

Authors: 01-hotfix.md → 02-shape.md → 03-slice.md → 04-plan.md. Branch: hotfix/<slug> off the production branch (suppressed when slug-attached). Terminus: gates, then /wf implement <slug> through the full chain to /wf retro.

refactor

/wf intake refactor <description>
/wf intake <slug> refactor <description>

refactor is the behavior-preserving quick lane. It captures a behavior baseline as the shape before any code moves. It plans incremental green steps and expects identical behavior after the change. Its review stage defaults to the refactor-safety dimension. When the run is slug-attached, it becomes one compressed slice on the named workflow.

Authors: 01-refactor.md → 02-shape.md → 03-slice.md → 04-plan.md. Branch: refactor/<slug> (opt-in; suppressed when slug-attached). Terminus: gates, then /wf implement <slug>.

update-deps

/wf intake update-deps [description]
/wf intake <slug> update-deps [description]

update-deps is the dependency-maintenance quick lane. It scans the manifests, researches each dependency, and prioritizes updates into risk tiers. Unlike the other quick lanes, it also self-authors the implement and verify stages, because its tier-ordered execution is specialized. It then routes straight to review and skips /wf implement and /wf verify. An audit-only run (plan saved, nothing implemented) ends lawfully with /wf close <slug> deferred, with every Hold entry recorded as a machine-readable revisit trigger; the next run seeds its research from the prior run's Hold and Blocked lists instead of cold-rescanning. A bare token that matches an existing run slug resumes that run. When the run is slug-attached, it becomes one compressed slice only.

Authors: 01-update-deps.md → 02-shape.md → 03-slice.md → 04-plan.md → self-authored 05-implement.md / 06-verify.md. Branch: deps/<slug>. Terminus: /wf review <slug>.

A dependency update records ux-impact: none, so it never waits for the design stage. When it upgrades a major version of a UI framework, component, or styling package, review adds the design-audit dimension to check the rendered surfaces for drift.

rca

/wf intake rca <symptom description>
/wf intake <slug> rca <symptom description>

rca is root-cause analysis for a reported failure whose cause is unknown. Parallel diagnosis sub-agents investigate. The result is a structured RCA with confidence, blast radius, and a suggested fix shape. The result also includes a synthesized minimal shape, so /wf plan can consume the workflow directly. rca never writes a fix. When the run is slug-attached, it becomes one compressed slice without the synthesized shape.

Authors: 01-rca.md + synthesized 02-shape.md + 00-index.md. Branch: none. Terminus: terminal — the routing decision is recorded via rca <slug> <route>. The plan route continues the same slug into /wf plan. When the suggested fix changes what a person sees or does, rca records the ux-impact, and the route goes through the design stage (/wf design <slug>) before plan; the fix and hotfix routes close this workflow and forward the diagnosis with from <slug>, so the successor inherits the root cause, blast radius, and verification criteria instead of re-deriving them. Human triage is the last rung of an escalation ladder (probe, study-sources, consult), not the only one.

investigate

/wf intake investigate <problem>
/wf intake <slug> investigate <problem>

investigate sketches solution options for an open design question. It enumerates every genuinely distinct candidate approach grounded in the existing architecture. Up to three approaches are presented as full cards with tradeoffs: scope, blast radius, effort, risk, reversibility, and the decisive unknown that could kill the option. Further distinct options are recorded compactly. The mode deliberately does not pick a winner; you pick the winner. Re-invoke it as investigate <slug> <option> to record the pick: the choice and your reason are stamped into the artifact, and the workflow closes. The mode is read-only apart from that bookkeeping: it writes no application code and does no bug diagnosis.

Authors: 01-investigate.md + 00-index.md. Branch: none. Terminus: terminal — you pick an option (recorded via investigate <slug> <option>), then /wf intake or /wf intake fix with from <slug> carries it forward, seeded from the investigation.

discover

/wf intake discover <hypothesis>
/wf intake <slug> discover <hypothesis>

discover tests a hypothesis against the codebase: "is X actually the case?" Parallel sub-agents argue for the hypothesis, argue against the hypothesis, and propose counter-hypotheses. The result is a verdict of holds, partial, fails, or inconclusive, with confidence and cited evidence. The mode is read-only.

Authors: 01-discover.md + 00-index.md. Branch: none. Terminus: terminal — the workflow closes at write time (verdict-recorded); a verdict leaves nothing to pick. The artifact records what decision rode on the verdict, and the verdict-dependent routes carry from <slug> — on fails, the ranked counter-hypotheses travel into the follow-on rca as candidate root causes.

audit

/wf intake audit <concern> [paths…]
/wf intake audit <audit-slug>           # accumulating re-run
/wf intake <slug> audit <concern>       # one-shot compressed slice

audit hunts unknown defects across a named subsystem. It exists for the request every adjacent surface refuses: review existing code for bugs, wrong assumptions, and mistakes when there is no symptom (rca needs one), no stated hypothesis (discover needs one), no decided problem (investigate needs one), and no diff (the review stage needs one). Parallel sub-agents first resolve the concern to a concrete file surface by four search modalities, and the surface is confirmed with you before any lens runs — an audit whose scope was silently guessed cannot be trusted when it reports "no findings". Review's existing rubrics serve as the lenses; the selection is stated with a reason per lens. Every candidate finding faces adversarial refutation before it lands (three refuters for a BLOCKER or HIGH), and refuted candidates are kept with their refutations. Survivors merge into the same accumulating findings ledger the review stage owns: a re-run preserves prior IDs, marks cleared findings resolved, and never overwrites. A finding that static reading cannot settle is recorded as needs-runtime-evidence with the exact experiment named, and routes to /wf probe. The mode is terminal and route-don't-fix: each accepted finding routes to its own follow-up command, and a zero-finding result is valid and legible. The workflow stays open for re-runs until you retire the concern with /wf close.

Authors: 00-index.md + 01-audit.md (the brief: surface, exclusions, lenses, not-observable set) + 07-review.md and one 07-review-<lens>.md per lens (the ledger). Branch: none. Terminus: terminal — each finding routes (fix, rca, investigate, full intake, probe, or task, all with from <slug>); re-invoke with the slug to merge new findings into the ledger.

ideate

/wf intake ideate [area]
/wf intake <slug> ideate [area]

ideate is proactive codebase ideation. It inverts the usual direction and surfaces work you might not have thought to ask for. Parallel sub-agents scan across six lenses: quality, performance, security, DX, feature gaps, and architecture. The sub-agents generate a large candidate pool, adversarially cull the weak ideas, and rank the survivors by impact and effort. Each idea keeps its file-and-line evidence on the machine-readable roster, and the idea you pick is recorded via ideate <slug> <idea-id>, which closes the workflow and prints the seeded successor invocation.

Authors: a lightweight workflow with the 01-ideate.md lead only (no build stages). Branch: none. Terminus: terminal — pick ideas (recorded via ideate <slug> <idea-id>, which closes the workflow), then the printed successor invocation with from <slug>.

brainstorm

/wf intake brainstorm <topic>
/wf intake brainstorm <brainstorm-slug>     # resume the board
/wf intake <slug> brainstorm <topic>        # compressed slice on a workflow
/wf brainstorm [slug] [design] [idea]         # the same loop under its own key

/wf brainstorm runs the same loop under its own key, and /wf intake brainstorm stays valid. The design focus concentrates the brainstorm on how an idea looks and behaves: it reads the design record, maps the design space, and draws rough sketches that stay ideas. At done, the design thoughts travel with each piece of work, and the design stage presents them again as its starting direction. See Commands and Design.

brainstorm is a thinking partner. You bring a half-formed thought and explore the problem and the solution space with the agent. You lead. The agent maps the areas the topic touches, goes wide before it goes deep, and brings ideas of its own, including concrete solutions. It never commits to a design: a choice that other work would build on, such as a data format, is recorded as a question for the plan. Each turn is a batch of one to four questions through the host's question tool, in plain words: every question explains what is known and why it matters before it asks, and no text you read shows an internal key or number. A reflection offers readings of your last thought, a probe targets one assumption, a fork offers directions, and a widen question brings a direction you have not raised. The agent works from principles, not quotas: it follows your last reply, raises a tension when it matters to what you are thinking about, and checks in at natural moments with a short summary of what we now believe, which you correct. The summary is in the question itself, because a question dialog can hide the text before it. When the ground is new to you — a research result, a specialist subject, or a question you ask — the agent takes a talk turn first: it explains in chat, with an example and its own view, and ends with an invitation to reply instead of a question. Say pause, or choose to stop at a check-in, and the agent tells the story of the sitting: what we explored, what we learned, what we decided and why, what is open, and where we start next. A resume opens with that story. After a list opens an area, the agent asks you to choose: an order, a trade-off, or a cut, with the cost of each option. When you set a risk aside or take the costliest option, and the consequence is material, it states the consequence once and records the risk you accept. When you answer with a mix, it writes the blend as one sentence for you to confirm. There is no question floor and no cap. Control words steer the loop from the first token of a free-text reply: park, pull, and drop a thread, board to show where we are, look it up to send one research sub-agent, second opinion to consult, cohere, pause, and done.

The board is two files with one truth. 01-brainstorm.md is your document, in plain prose. It opens with a short front: the summary, a brief of five lines or fewer per area, and what is open now. The full record follows: the decisions with their reasons, the open ideas, the findings with their sources, the assumptions, the tensions, and the questions for the plan. Where the host can publish a page, the agent also keeps the board as a live page and gives you its link. brainstorm-board.json is the agent's working board, with a readable key for every item, and the write hook validates it on every write. Both are rewritten after every batch, so a resume never re-asks what the board answers. A board from before this layout converts on its first resume. When an area feels explored, the check-in offers to close it: it shows the area's price against the budgets you set, you name what is core, choose the first version (the rest waits for later, and nothing is cut unless you say so), pick the risk that worries you most, and say whether it changes work that already exists. A coherence pass then checks the board against itself, against the documents of work it already routed, and against your budgets; say cohere to run one at any time. When you paste a brief or name a file, the agent maps each of its criteria as covered, partial, or open, and walks the gaps with the same depth for each. Only you end the loop. On done you choose to scope the work now, keep the board for later, or take a second opinion. To scope, you and the agent walk back through the areas you have not closed yet, one at a time: you keep, cut, or leave for later each area or each item, and the agent flags a kept item that needs one you cut. Then you agree how the kept items become work — what comes first, how they group, the order, the size, and the form of each piece. Nothing is written until you confirm; then each piece of work gets one entry command with from <slug>, and nothing runs. The successor inherits only what you kept.

Authors: a lightweight workflow with the 01-brainstorm.md document and its brainstorm-board.json (no build stages). Branch: none. Terminus: terminal and stays open — done scopes the work with you, and the pieces of work you agree route (intake, investigate, fix, discover, task, or an extension, all with from <slug>; a design brainstorm adds /wf design <slug> and /wf design direction from <slug>); resume with the slug, which reopens a distilled board; retire with /wf close <slug> when no thread is live.

adopt

/wf intake adopt

adopt is the reverse entry. Every other mode assumes the change lies ahead. Adopt reads the change you already made in the working tree and reconstructs the planning-and-execution artifacts from what the code does. It stamps each artifact provenance: adopted, behind a confirm-before-write gate. The workflow lands at verify, so the quality tail (verify, review, handoff) runs over work done outside the pipeline. Adopt is standalone only: it can never attach to a slug, and it is never auto-proposed. It records the current branch and never creates a branch.

Authors: 01-adopt.md → 02-shape.md → 03-slice.md → 04-plan.md → 05-implement.md, all reconstructed. Branch: records the current one; never creates one. Terminus: /wf verify <slug>.

extension (keywordless)

/wf intake <existing-slug> <new scope>
/wf intake <existing-slug> from-review
/wf intake <existing-slug> from-retro

Extension is the one route with no keyword at all: an existing slug followed by free scope text is the signal. Extension adds net-new slices to that workflow, as full per-slice files, never as a compressed slice. Extension never modifies completed work. Scope corrections and follow-on work land here, because built work is never re-specified in place. The from-review, from-retro, from-probe, and from-simplify seeds pull the new scope from findings instead of free text. Extending a closed workflow is valid and revives it. A workflow with no slice roster yet — one that has not reached slicing, or a terminal analysis mode — is guarded at the entry: extension routes you to the workflow's own next stage or to the analysis mode's decision recording instead of failing on a missing roster.

Authors: full net-new 03-slice-<new>.md file(s) plus a non-destructive master-index update. Branch: the workflow's existing one. Terminus: /wf plan <slug> <new-slice>. When the new slices add surfaces or states that the confirmed design does not cover, extension reopens the design, and the terminus is /wf design <slug> amend. No plan for a new slice can be written until the person confirms the new drawings.

amend

/wf intake <existing-slug> amend <what to change>

amend is a maintenance mode and requires a slug. Amend edits a workflow's recorded configuration in place, against a strict whitelist: branch strategy, branch, base branch, review scope, title, and tags. Amend edits nothing else. Anything outside the whitelist routes elsewhere: new scope is an extension, and wrong behavior is a fix slice. Amend writes no numbered artifact, writes no slice, and never touches built work.

Authors: edits to 00-index.md and the registry row only. Branch: n/a. Terminus: whatever the workflow was already doing.

modernize

/wf intake <existing-slug> modernize

modernize is a maintenance mode and requires a slug. Modernize backfills an older workflow's artifacts to the schema the installed plugin now expects: charter, intent-risk ledger, wall-ownership and clearing-event fields on deferrals, and revision ledgers. Modernize is strictly additive: it fills absent fields from what the artifacts already say, and it never rewrites a recorded decision, verdict, or acceptance criterion. Intake also detects schema drift automatically when you extend an old workflow, and it offers modernize then.

Authors: additive field backfill across the workflow's existing artifacts. Branch: n/a. Terminus: the command that resolves the largest remaining gap.

Runtime verification (/wf probe) and read-only triage (/wf simplify) are not intake modes. They act on already-built or existing code, so they are top-level keys of their own.
