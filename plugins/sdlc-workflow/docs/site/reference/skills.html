Standalone skills

This page is the lookup reference for the plugin's skills outside /wf: /consult, /diataxis, and /study-sources. It also covers the two internal skills that design runs mention but that you cannot invoke yourself.

The three user-invocable skills share a family resemblance with the /wf commands: positional arguments, no flags, and a keyword in first position when you want to narrow the run. None of the three belongs to a workflow. You can use any of them in any repository, at any point, with or without an active workflow.

/consult — a read-only panel of external models

/consult sends a question to one or more external AI models that act as read-only oracles. It brings back their written opinions: a plan critique, a code or implementation review, a design trade-off analysis, a diagnosis, or a second opinion. Ask for one:

/consult <question>
/consult codex <question>
/consult anthropic/claude-opus-4-8 <question>

Provider resolution

The first token of the arguments decides who answers. A provider keyword (codex, claude, gemini, or openai) pins that provider, and the rest of the line is the question. A <provider>/<model> token (any token that contains a /, such as openai/gpt-5.5) also pins that provider, routed through the Vercel AI Gateway. Otherwise the whole line is the question, and the run fans out to every available provider in parallel. The fan-out is the default.

The providers fall into two classes, and the difference matters when you read the answers:

ClassProvidersEvidence scopeCost
CLI oraclescodex, clauderepo-aware: they run with the repo as working directory and read the live tree themselvesFree (subscription CLIs, no per-call charge)
REST oraclesgemini, openai, gateway <provider>/<model>prompt-only: they see nothing but the prompt, so relevant file or diff content is inlined for themBilled per-token to your API key on every invocation

To stay free, pin a subscription CLI: /consult codex <question> or /consult claude <question>.

A bare fan-out hits every available provider, including the paid ones.

The read-only guarantee

Consult is advisory only. The dispatched sub-agents can read the repository (Read, Glob, Grep) but cannot edit, write, or run shell commands. The runner spawns the CLI oracles isolated and read-only. The runner script itself enforces this restriction, not only the skill's prose. A consult never writes code and never proposes a patch that it could apply. A consult run produces only its own ephemeral prompt files under .ai/consult/. When the question targets a workflow artifact, the run can also write an optional narrative fragment that embeds the panel beside that artifact.

The panel

The result is presented as a panel. For each provider that answered, the panel shows its evidence-scope badge (repo-aware or prompt-only), a one-line verdict, and the key points. A one-line consensus-or-divergence read across the panel follows. Providers that were skipped or that failed are named with their reasons. A degraded panel announces itself up front ("Panel of 1 — treat this as one opinion, not a consensus") instead of reading with the confidence of an agreement it never earned. When a prompt-only oracle disagrees with a repo-aware oracle on a repo-specific claim, the synthesis weights the repo-aware opinion more heavily. The synthesis also says when a divergence looks like missing context rather than real dissent. Every run ends with a machine-readable CONSULT_RESULT block that records the providers, the panel size, the verdict, and the cost note.

Auto-invocation

You do not have to type /consult for it to run. The model auto-invokes the skill at the judgment points that the lifecycle stages call out: plan, shape, design, review, verify, and handoff, and their equivalents inside the /wf auto and /wf yolo drivers. The skill runs whenever a stage's objective trigger fires: a carried intent-risk, a ship-with-caveats verdict, an acceptance criterion that was inferred rather than observed, or a risk-bearing surface. These triggers are written into the stages themselves. A second opinion at those gates is a default action, not a rare one. Every model-initiated run pins a free subscription CLI (codex or claude), so autonomous consults never touch the paid REST oracles. The "use sparingly" caution applies to provider choice, not to frequency. Consult is never triggered by a hook or by page serving. Only a deliberate model or user decision starts a consult.

/diataxis — standalone documentation work

/diataxis writes or reviews documentation under the Diátaxis framework. The framework splits documentation into four modes that serve four distinct needs, plus two supporting activities (a planner and a reviewer). Invoke the skill with an optional mode keyword:

/diataxis [tutorial|how-to|reference|explanation|readme|plan|review] <what to document>

The four quadrants, at a glance:

Practical stepsTheoretical knowledge
Serving study (acquiring skill)Tutorial — learning-orientedExplanation — understanding-oriented
Serving work (applying skill)How-to — task-orientedReference — information-oriented

The one rule the skill enforces is boundary discipline: each page serves exactly one mode. The most common documentation failure is a mixed page, for example a tutorial mixed with reference tables, or a how-to padded with conceptual background. The skill therefore classifies the request first, then writes to that mode. If your request opens with an explicit mode keyword, the classification is skipped. If your request is ambiguous or spans a whole docs set, the request routes through the planner first. Beyond the four quadrants, readme handles front-door pages, plan maps a docs structure, and review audits existing docs against the framework.

When to use /wf docs instead. This skill is the general-purpose, standalone documentation surface: any repo, any docs request, outside a workflow. /wf docs is the lifecycle-bound counterpart. It writes documentation as .ai/ workflow artifacts with frontmatter and index bookkeeping, and in workflow mode it fulfills the shape stage's Documentation Plan. The Diátaxis discipline is the same; the home is different. A request to document a slug or a shipped feature inside an active workflow belongs to /wf docs. Every other documentation request belongs to /diataxis.

/study-sources — read real upstream source

/study-sources grounds your work in real upstream source code rather than recalled API shapes. Some tasks turn on how a library, framework, or SDK actually behaves: an exact function signature, an edge case, an error string, or a version-specific change. For those tasks, this skill fetches the source so the source can be read instead of guessed at. The skill accepts three source forms:

/study-sources <git-url> <what to learn>
A Git host URL (GitHub, GitLab, Bitbucket, and so on) is treated as a clone request. The clone is shallow (--depth 1), sparse for large monorepos, and at the tag that matches the version the project resolved.
/study-sources <package>@<version> <what to learn>
A package coordinate routes to that ecosystem's fetch path (source JARs, pip download, npm pack, cargo vendor, and so on).
/study-sources <ecosystem> <what to learn>
An ecosystem keyword routes to that ecosystem's reference directly. With no keyword at all, the skill infers the ecosystem from the project's manifests.

Two habits make the skill reliable. First, the skill reads what is installed before it clones. Most ecosystems already cache decompressed source locally: node_modules/, ~/.m2, the Gradle, Cargo, NuGet, and Go module caches, Python site-packages, and the Android SDK's sources/. To read the version the project actually resolved is faster and more correct than to clone an upstream main that may be ahead of the pinned release. The network is a fallback, used only when the source is not already on disk.

Second, everything fetched lands in .scratch/, a gitignored directory, with one sub-folder per source (for example .scratch/sources/<ecosystem>/<name>@<version>/). Cloned repos and unpacked archives therefore never pollute the working tree, git status, or the project's history. If .scratch/ is not yet ignored, the skill adds it to .gitignore before it fetches.

The skill is read-only: it fetches source to study, never to build, install, run, or execute. To pull a dependency down in order to run it is a dependency-adoption task, not a study task, and is out of scope. The skill is available at any lifecycle stage or with no workflow at all.

The two internal skills

Two more skills ship with the plugin but are not user-invocable. You will see them named in /wf design output, and that is the only place they run:

imagery
Generates images from a text prompt. It fans out to the available providers (the built-in image_gen tool, gpt-image-2, nano-banana) to produce a variant set, or produces a single image when a provider is pinned. Generated images land in .ai/design-probes/ and are embedded as data-URI fragments beside the design artifact. /wf design uses imagery for visual-contract mocks. The imagery result sets the image-gate line that every design run reports.
uiproto
Prototypes a UI component or screen from a prompt. It fans out to Google Stitch and an LLM HTML generator side by side, or to one of the two when a provider is pinned. The result is a self-contained HTML fragment embedded in a sandboxed <iframe srcdoc> next to the design artifact, so a full generated screen's CSS cannot leak into the page. The Stitch engine needs STITCH_API_KEY and STITCH_PROJECT_ID in the environment.

The consent gate: externalDispatch.enabled

Both internal skills send your prompt to third-party services. Both are therefore gated behind a single machine-wide consent flag: externalDispatch.enabled in ~/.sdlc/hub-config.json. The flag is off by default. Until you turn the flag on, imagery falls back to its no-egress paths (the built-in image_gen tool and a text-only fallback). Until you turn the flag on, uiproto stops with a one-line opt-in notice, because uiproto has no no-egress fallback. The skill runner scripts re-check the flag themselves, so a direct script invocation cannot bypass the flag.

/consult is deliberately not behind this gate. Consult runs on demand, and its cost discipline is the free-CLI pinning rule described above, not a consent flag. The read-only sandbox around consult's sub-agents is independent of consent and always applies.
