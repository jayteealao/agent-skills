Installation

This page shows how to install the sdlc-workflow plugin into Claude Code or Codex, and what happens in your first session. One plugin directory serves both hosts. Two quick checks confirm that the plugin runs.

Commands on this site are written as /wf …. Under Codex, type $wf … instead. The key and the arguments are the same.

What you need first

The plugin runs inside Claude Code or inside Codex. Its background work (the hub daemon, the render pipeline, and the hooks) uses Node.js 20 or newer. Both hosts already require Node.js, so there is nothing extra to install. The one real precondition is git: the plugin registers each project by its git identity, and workflow branches live in git. If you run /wf in a directory that is not a git repository, the command stops and explains why. The command then offers to run git init for you. The plugin never initializes a repository without asking.

The plugin is distributed through one marketplace, hosted in the jayteealao/agent-skills GitHub repository. Each host has its own catalog file in that repository and its own install commands. Pick the section for your host.

Install into Claude Code

Inside Claude Code, add the marketplace:

/plugin marketplace add jayteealao/agent-skills

Then install the plugin from it:

/plugin install sdlc-workflow@agent-skills-marketplace

When the install completes, start a fresh session in the project where you want to use the plugin. Claude Code runs the plugin's hooks with no trust step.

Install into Codex

Codex needs a build with the plugin and hook features enabled. The plugin is verified on Codex CLI 0.146.0. Confirm both features:

codex features list

The plugins and hooks rows must read true. When a row reads false, enable it with codex features enable hooks and codex features enable plugins. Then add the marketplace and install the plugin:

codex plugin marketplace add https://github.com/jayteealao/agent-skills
codex plugin add sdlc-workflow@agent-skills-marketplace

Codex installs a snapshot of the plugin directory. Codex runs no hook until you trust it. Open an interactive Codex session in any repository and run:

/hooks

Trust all seven hook events (SessionStart, SubagentStart, PreToolUse, PermissionRequest, PostToolUse, Stop, SubagentStop). Untrusted hooks are skipped without an error, so this step decides whether validation and rendering work at all. An upgrade that changes the hook file asks for trust again.

From the plugin's installed directory, a doctor script reports the machine state: the CLI version, the two features, the enabled plugin, the trust state, and any leftover of the older sdlc-workflow-codex plugin identity:

npm run verify:deployment
Older installs used a separate plugin named sdlc-workflow-codex. That plugin is retired; the same source now serves both hosts under the name sdlc-workflow. To move a machine over: close every Codex session, run codex plugin marketplace upgrade agent-skills-marketplace, then codex plugin add sdlc-workflow@agent-skills-marketplace, then codex plugin remove sdlc-workflow-codex@agent-skills-marketplace, then trust the hooks in the next session. Do not open a session while both plugins are enabled: two plugins would expose two wf skills and run two hook sets against the same repository.

What happens on the first session

The plugin ships hooks that the host runs automatically at the start of every session. All hooks run in the background. None of them injects anything into your conversation. On a healthy install, none of them needs your attention. Three things happen:

The hub starts. The hub is a single machine-wide daemon on 127.0.0.1:4173, and it registers your repository. The hub serves a rendered, browsable HTML view of every workflow artifact the plugin writes. Each repository gets a dashboard, and the dashboard reloads live as artifacts change. One hub serves every registered repository on your machine, whichever host registered it. When you install into a second project, the plugin registers that project with the same hub.

The render bootstrap runs. The session-start hook enqueues a whole-repo render of the dashboard, and the hub drains that queue in the background. From then on, the hub renders every workflow artifact that a session writes.

Your instruction files get a rules block. The plugin seeds a small fenced block of /wf usage rules into AGENTS.md at your project root. It also seeds an @AGENTS.md import into CLAUDE.md. The working conventions then travel with the repository, and both hosts read them. The plugin owns only its own fenced block. The rest of both files is yours. The seeding is fail-open: if anything goes wrong, the plugin does nothing rather than break your session.

You can turn off individual pieces of this behavior. SDLC_DISABLE_BOOTSTRAP=1 skips the render bootstrap, and SDLC_DISABLE_MEMORY_SEED=1 skips the rules seeding. The full list of switches is in Configuration.

Confirm that the plugin runs

Make two checks: one inside your host and one in your browser. First, run the command with no arguments:

/wf

The command must show a menu of all 22 keys: the ten lifecycle stages plus the standalone commands. The command then asks which key you want. If you see that menu, the plugin is installed and dispatches correctly. Under Codex, the menu shows the same keys; only yolo is unavailable there.

Second, open the hub in your browser:

http://127.0.0.1:4173

The dashboard must list your registered repository. The hub also exposes a plain health endpoint at http://127.0.0.1:4173/__sdlc/health. The endpoint is useful for scripts, or for a quick check from the terminal that the hub is up.

A brand-new project shows an empty dashboard, because there are no workflows to render yet. That is normal. The dashboard fills in when your first /wf intake writes its artifacts.

Optional: the tray app

On desktop machines, you can run a small notification-area app that watches the hub for you. The icon and tooltip of the tray app show hub health. The tray app polls the hub every five seconds. The tray menu opens the dashboard, opens per-repository views, and restarts or stops the hub. The tray menu also offers a start-at-login toggle, so the tray app starts again after a reboot.

You launch the tray app yourself, outside the host. From the plugin's installed directory, start the tray app with:

npm run tray

That command runs node dist/tray.mjs, so you can also invoke the file directly. When you enable Start at login from the tray menu, you never need to launch the tray app by hand again. On Windows, the session-start hook also keeps an enabled autostart entry pointed at the current plugin version across upgrades.
