Quick lanes

Four intake modes (fix, hotfix, refactor, and update-deps) run the planning half of the standard lifecycle in a single pass. This page explains what each lane authors, where it stops, and what you run next.

The shared model

A quick lane is not a shortcut around the lifecycle; it is the same lifecycle with the ceremony compressed. One run of /wf intake <mode> <description> authors real, schema-conformant artifacts for stages 1 through 4, all under .ai/workflows/<slug>/. The artifacts are the intake brief, the shape, a single-slice slice index, the plan, and the workflow's index file. No stage is skipped; each stage is written single-pass instead of interactively. Every lane is a single-slice workflow: the workflow slug doubles as the one slice's name, and the downstream stages write un-suffixed files (05-implement.md, not 05-implement-<slice>.md).

Then each lane stops at a gate before implementation and asks you to choose: Proceed, Adjust (revise a planning artifact, then the lane asks again), or Escalate (the work outgrew the lane; restart it as a full /wf intake). A clearly low-risk change may proceed through the gate without a pause, but the lane records the decision either way. Escalation is offered, never forced. If planning reveals that the work is bigger than the lane's envelope, the lane records the breach and keeps the plan valid; it does not refuse.

Past the gate, the standard chain takes over: /wf implement, /wf verify, /wf review, and onward to handoff and ship. The compression is in planning ceremony, never in stages or quality gates. One lane, update-deps, is the exception; its section below explains the difference.

fix — small intentional changes

/wf intake fix the export button label says "Exprot"

fix is the general-purpose small-change lane. It asks at most two planning questions and grounds itself with a targeted read of the files likely in scope. It writes a plan of at most five steps; each step names the files it touches and states how to verify the step. The lane works on a dedicated fix/<slug> branch by default (you can decline and stay on your current branch). Design work is never auto-included. If the change touches UI, the shape notes a follow-up recommendation instead of a block.

The fix lane watches its own envelope with tripwires: more than 3 files, more than 5 steps, a new external dependency, an architectural change, or too many unanswerable questions. A tripped wire does not stop the run. The lane records the tripped wire in the plan, and the gate's Escalate option is the suggested exit.

The lane stops at the gate, with planning complete. Next, run /wf implement <slug>.

hotfix — production incidents

/wf intake hotfix checkout returns 500 for all users

hotfix is the incident lane. Three differences from fix matter:

It branches off production. The branch is always hotfix/<slug>, created from the production/default branch, not from whatever you have checked out. The fix can then ship without unreleased work attached.

It diagnoses before it plans. The brief asks at most three questions: what is broken, what is the impact, and what changed recently. Then parallel investigators trace the root cause to specific files and lines and map the blast radius: callers, sibling components that share the bug, and data that may be corrupted. The diagnosis becomes the shape.

Scope is locked. The only acceptable output is the minimum change that stops the incident: no refactoring, no cleanup, nothing outside the identified root cause. The plan is capped at five steps across at most three files, and the plan must include an exact rollback. For anything bigger, take the gate's Escalate option.

The lane stops at the gate. Next, run /wf implement <slug>, then verify. Then run /wf review <slug> security; review defaults to the security dimension for hotfixes. Then run /wf ship.

refactor — restructuring without behavior change

/wf intake refactor untangle the auth service from the session store

refactor is the behavior-preserving lane. Its defining move is the baseline. Before any code changes, the lane snapshots the public API surface exactly as it exists, maps which behaviors the tests actually cover, names the coverage gaps, and records the current test results. That baseline is the shape, and the baseline becomes the acceptance contract. At verify, every exported name must still exist with the same signature, and the suite must match the baseline counts. If the gaps are significant, the lane asks whether to add tests first, before it touches anything.

The plan is a sequence of atomic steps that each leave the build working and the tests green, following a named refactoring pattern. Hard rules apply: no new functionality, and no public API changes unless the stated goal is to simplify the API. Never skip or rewrite a failing test. A test that fails after your change is a regression in the refactor, not in the test.

The dedicated branch is opt-in rather than the default: the lane asks whether to create refactor/<slug> or stay on the current branch.

The lane stops at the gate. Next, run /wf implement <slug>: one green step per plan step, each committed individually. Then verify against the baseline. Then run /wf review <slug> refactor-safety.

update-deps — dependency maintenance

/wf intake update-deps

update-deps is the exception among the four. The other lanes hand execution to the standard chain. update-deps authors its own implementation and verification records in the same run, because tier-ordered dependency execution is specialized work that the generic implement stage should not improvise. /wf implement and /wf verify redirect an update-deps workflow back to the lane. The first standard command that accepts the workflow is /wf review.

The run scans every package manifest in the project, researches each outdated package, and sorts the work into tiers:

TierWhat is in the tierHow the tier is executed
P0 — securityPackages with an active CVE and a fix versionFirst, one package per commit
P1 — major + migrationMajor bumps with breaking changesOne at a time, migration applied, each its own commit
P2 — safe batchMinor and patch updatesOne batch (up to 10), full suite after
HoldIncompatible, peer-blocked, or unverifiableNot updated; reason and revisit condition recorded

The research is grounded, not guessed. Each package's breaking changes and migration steps must cite the package's own changelog or release notes, and the research reads every intermediate major between the current and target versions. A P1 package whose changelog cannot be verified does not get an optimistic plan; the package drops to Hold. When a package's update breaks tests in a non-trivial way, the lane marks the package blocked and leaves it at its old version rather than bend application code. A verify result of partial (some packages updated, some blocked) is a legitimate outcome. The lane touches lockfiles only through the package manager's own commands.

Arguments narrow the run. A package name focuses the run on one dependency. --security-only updates only CVE-affected packages. --audit-only produces the scan, the research, and the plan, then stops at the gate without implementation. The gate itself is tier-aware: you can proceed with the full plan, proceed with P0 security updates only, save the plan as an audit, or adjust.

The lane stops after its own verify. Next, run /wf review <slug>, then handoff and ship.

Attached to a workflow vs standalone

Everything above describes a standalone run: a new workflow, its own slug, its own branch. But every lane can also attach to a workflow you already have. Name the existing slug before the mode:

/wf intake reports-export fix date column renders as epoch millis

An attached run keeps the lane's full analysis discipline but reroutes the output. Instead of a new workflow, it writes one quick-lane slice, 03-slice-fix-<descriptor>.md, in the named workflow's directory. The slice carries the same content the standalone artifacts would hold. The run creates no new workflow and no new branch (the lane's branch step is suppressed), and the parent workflow's lifecycle position does not move; the slice is purely additive bookkeeping on the existing index. Use the attached form when the small work belongs to a feature already in flight. Use the standalone form when the work deserves its own history and its own branch.

Attachment is one form of intake's slug-first convention. The neighboring form, an existing slug followed by free scope text instead of a mode keyword, is an extension. An extension adds full new slices rather than a quick-lane slice. Choose your entry covers the resolution order.
