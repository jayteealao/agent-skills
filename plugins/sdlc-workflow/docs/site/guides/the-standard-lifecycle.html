The standard lifecycle

Read this page when you are about to run a serious feature end to end. It walks all ten stages in order and shows what each stage is for, what it asks, what it writes, and where its gate can stop you.

The standard lifecycle is ten stages. You run the stages one at a time, each as its own /wf invocation:

intake → shape → slice → plan → implement → verify → review → handoff → ship → retro

Every stage writes its result as a numbered artifact under .ai/workflows/<slug>/ before it says anything in chat. The file is the record; the chat summary is the courtesy copy. Stages build strictly on their predecessors: each stage starts with a read of the control file 00-index.md and the earlier artifacts. When a prerequisite is missing or still marked awaiting input, the stage stops with a clear message. You are the product owner (PO) throughout. The early stages interview you, the later stages gate on your decisions, and every answer you give accumulates in po-answers.md.

Standing instructions travel with the workflow. When a steer.md file exists in the workflow directory, every stage reads the file before it does anything else and honors your standing instructions, both in the stage's own work and in every sub-agent the stage dispatches. Steering never overrides a mandatory gate, but steering shapes everything beneath a gate. One written line, such as "always run the mobile viewport too" or "never touch the legacy auth module", applies at every stage without repetition.

Stage 1 — intake

Intake is the front door. Run it with a plain description of what you want:

/wf intake add offline support to the notes editor

The default flow interviews you as the product owner: what problem the work solves, who the work is for, what is out of scope, and how big your appetite is. It also fingerprints the repository's stack (languages, platforms, tooling) and asks you to confirm the fingerprint, because later stages make tooling decisions from the fingerprint rather than re-detect the stack. Intake writes two files: the control file 00-index.md, which every later stage reads first, and 01-intake.md, the brief. Intake also starts the intent-risk ledger, a record of load-bearing ambiguities in what you asked for. Shape must resolve each recorded ambiguity, and handoff and ship refuse to ignore an open one.

Intake also has mode keywords (fix, hotfix, rca, investigate, and others) that route quicker or standalone entries. For a serious feature, use the default flow. The other entries are described in Choose your entry and Quick lanes.

Stage 2 — shape

Shape turns the brief into a compact, implementable mini-spec with explicit acceptance criteria and edge cases:

/wf shape <slug>

Shape is the most question-heavy stage. It launches research sub-agents into the codebase, and into the web when external knowledge matters, while it interviews you. It asks structured PO questions for decisions such as risk tolerance and appetite, and freeform questions for behavior, acceptance criteria, and non-goals. Shape also adjudicates the intent-risk ledger: you must resolve every open ambiguity that intake recorded, or consciously carry the ambiguity to a named later stage. Shape writes 02-shape.md.

Two kinds of optional work attach at shape. First, when the feature has a visual surface, shape authors the design brief, 02b-design.md: content inventory, states (empty, error, loading, first-run), and visual direction. Slice and plan then treat the design brief as mandatory input. Second, shape decides which add-ons the work needs (instrumentation, an experiment, a performance benchmark) and records the decision in the shape artifact's augmentations-needed frontmatter. Shape decides; plan authors. You never invoke the add-ons directly.

Some spec errors are expensive downstream: a new capability, multiple slices, or a carried intent-risk. In those cases, shape automatically gets a second opinion on its draft acceptance criteria from an external model before it writes the file.

Stage 3 — slice

Slice decomposes the shaped spec into thin, independently verifiable vertical slices:

/wf slice <slug>

Before slice cuts, it interviews you briefly about decomposition strategy: genuinely different ways to split the work. Each way is described by what you experience, for example more PRs and faster feedback versus fewer review passes, not by mechanism. If a design brief exists, its states and surfaces must inform the slice boundaries. A distinct state or visual surface either gets its own slice, or the master index justifies the grouping in one sentence.

Slice is also where you answer the review-scope question, exactly once per workflow: review each slice separately (one review artifact per slice), or review the whole slug against its cumulative diff (one artifact). Slice records the answer in 00-index.md, and review and handoff trust the answer from then on. Slice writes the master index 03-slice.md plus one 03-slice-<slice>.md per slice. Each per-slice file carries that slice's acceptance criteria.

Stage 4 — plan

Plan produces an execution-ready implementation plan for one slice (or all of them in parallel):

/wf plan <slug> <slice>

Plan inspects the repo, runs a reuse scan, and writes concrete steps with a verification strategy per acceptance criterion. When a criterion needs a special environment (credentials, a device, an external service), the plan states explicitly how that evidence will be produced. That forethought matters later: verify refuses to quietly pass a criterion whose evidence path was never engineered.

Plan is where the optional layers become concrete. If a design brief exists but no visual contract exists yet, plan authors 02c-craft.md: the mock fidelity inventory and the implementation contract that implement builds against and verify re-checks. For each add-on that shape decided, plan authors the matching artifact: 04b-instrument.md (signal design), 04c-experiment.md (flag, cohorts, metrics), or 05c-benchmark.md (baseline numbers). Plan records each add-on in the augmentations: list in 00-index.md, so implement and verify consume the add-ons without being told. Plan writes 04-plan.md plus 04-plan-<slice>.md per planned slice. By default, plan gets an external second opinion on any plan that touches risk: concurrency, auth, migrations, money, external APIs, or open unknowns.

Stage 5 — implement

Implement writes the code for one selected slice, exactly as planned:

/wf implement <slug> <slice>

Implement reads the slice definition, the plan, the shape, and every add-on artifact before it touches code. It deliberately does not verify, review, or broaden scope. It treats the visual contract's inventory items as acceptance criteria. Instrumentation signals must actually be added, and experiment wiring must actually exist. When the code calls a dependency whose exact behavior matters, implement reads the installed source rather than guess at a remembered API. Any claim that a library cannot do something must carry evidence. Implement writes 05-implement-<slice>.md. The artifact records what was built, what deviated from the plan and why, and anything deferred.

Later, after review, the same command returns in a second role: /wf implement <slug> reviews fixes the findings that review triaged as must-fix, one by one.

Stage 6 — verify

Verify checks that the slice actually meets its acceptance criteria:

/wf verify <slug> <slice>

Verify runs the mechanical checks (tests, lint, typecheck, build) and then the acceptance-criteria gate: direct observation must confirm every user-observable criterion. Direct observation means a run of the artifact and a look at the output, not inference from the code. Each add-on gets a type-specific re-check: instrumentation signals must demonstrably fire, experiment flags and cohort splits must work, and the benchmark re-runs against its baseline and flags regressions.

When something fails, verify owns a single, user-gated fix loop. It triages every failure with you (fix, skip, or escalate), dispatches sub-agents to apply the minimal patches you approved, re-runs only the affected checks once, and finalizes. There is one round only. If anything still fails after that round, the artifact records the escalation and routes you to re-run verify or to return to implement. Verify never loops silently until green. Verify writes 06-verify-<slice>.md with the evidence, and a write-time hook hard-blocks any verify artifact that claims a pass while criteria are unmet. When evidence genuinely cannot be produced in this environment, verify records a deferral in 00-index.md: a ship-blocking IOU, not a forgotten footnote.

Stage 7 — review

Review is the quality gate before the work leaves your machine:

/wf review <slug>

Review reads the workflow artifacts and the diff, selects the review dimensions relevant to the change, and dispatches one reviewer sub-agent per dimension in parallel. Findings land in an accumulating ledger: 07-review.md, or one ledger per slice, per your review-scope answer. Re-runs merge into the ledger: duplicates are deduplicated, cleared findings are marked resolved, prior triage decisions persist, and the file is never overwritten.

Review triages every blocker- and high-severity finding with you: fix, defer, or dismiss. Fix decisions run a fix loop on the spot. The verdict then derives from what remains open: ship (no open blockers or highs), ship-with-caveats (open highs only), or dont-ship (any open blocker). Pre-existing defects on the base branch are surfaced as debt and routed to their own fix workflows; they never count against this change's verdict. Deferred findings are not lost: /wf review <slug> triage revisits them later without a re-run of the whole review.

Stage 8 — handoff

Handoff packages the completed slices into a PR with reviewer and QA context:

/wf handoff <slug>

Before handoff packages anything, it runs a readiness check across every prerequisite: implementation records exist for every slice in scope, the required review artifacts exist, no review verdict is dont-ship, and no open blockers remain. One more check is a hard block: no intent-risk ledger entry may still be open. An open entry means that shape never resolved a load-bearing ambiguity, so handoff routes you back to /wf shape to adjudicate the entry rather than package around it. Consciously carried risks are legal, but the PR body surfaces them so the human reviewer sees them. Handoff also pre-checks the project's ship plan (.ai/ship-plan.md), the release contract. If the ship plan is missing or drifted from the repo, the run stops and routes to /wf ship-plan before any PR is declared ship-ready.

Then handoff pushes the branch, opens the PR, and waits for CI to reach a terminal state; a pending snapshot is not an answer. It writes 08-handoff.md with the result of the readiness check. When several workflows share one branch, /wf handoff pr#N covers all of them in one batch run with a branch-level readiness check.

Stage 9 — ship

Ship runs the release, with the project's ship plan as a contract:

/wf ship <slug>

Ship refuses to start unless handoff's readiness check came back ready, and it re-checks the two hard blocks at the door: any still-open runtime-evidence deferral and any still-open intent-risk entry stop the run. Earlier stages warn about these blocks; ship is where the block fires. Ship then asks every load-bearing question up front (scope, version, rollout) and walks a 13-step idempotent sequence: pre-flight through dry-run, go/no-go, merge, tag, and post-publish checks. It writes 09-ship-run-<run-id>.md as it goes. The sequence is replayable: a failure mid-run pauses at the failed step, and a re-run resumes there instead of repeating side effects. /wf ship <slug> rollback reverses a completed run. Batch mode ships every slug on a branch atomically, all or nothing.

Stage 10 — retro

Retro closes the loop:

/wf retro <slug>

Retro reads the entire artifact trail, including the design artifacts and add-on outcomes, and extracts what actually happened: where the plan drifted, what verification caught late, and which questions came too late. It proposes concrete, copy-paste-ready improvements to prompts, tests, and automation without applying them, and it distills durable lessons for future workflows. It writes 10-retro.md, and the workflow is complete.

If ten commands by hand feel heavy, /wf auto drives the same stages end to end and pauses at each stage's own gate: same lifecycle, one driver. See Autonomous drivers.
