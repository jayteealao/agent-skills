Design

This page shows how design runs in a workflow. A person confirms the design in the design stage, between shape and slice, before any stage that a driver can run. The same /wf design key also keeps the project's design record and runs design reviews on demand.

Commands on this site are written as /wf …. Under Codex, type $wf … instead. The key and the arguments are the same.

The design stage and why a person runs it

The design stage is a lifecycle stage. It sits between shape and slice, and only a person runs it. The stage turns the design brief into a drawing, and the person confirms the drawing. Every later stage then builds against a decision that a person made.

A driver can plan, build, and verify. A driver cannot know what the person wants the product to look like. For that reason, /wf auto and /wf yolo never run the design stage. If a driver invokes it, the stage stops and routes the person to /wf design <slug>.

The stage does these steps:

  1. It loads the project's design record (see The design record). When PRODUCT.md is missing, it runs /wf design setup with the person first.
  2. It makes sure that the brief 02b-design.md exists. Shape usually writes it. When it is missing, the stage writes it now.
  3. It inspects the code: the existing surfaces, tokens, and components that the brief touches.
  4. It draws every changed surface of the whole feature, not one slice. Every surface in the brief gets a drawing, in every state that the brief names. For a flow change, it draws the flow as a sequence of states.
  5. It asks the person one question: approve, adjust, or stop. On adjust, it changes the drawings and asks again. On stop, it writes no contract.
  6. On approve, it writes the visual contract 02c-craft.md. The contract records the canvas link (canvas:), who confirmed the direction (direction-confirmed-by:), when (confirmed-at:), and every surface drawn (surfaces:).

The next step is /wf slice <slug>. You can also start /wf auto <slug> or /wf yolo <slug> now, because the design is settled.

Design is settled when 02c-craft.md carries a resolved image gate and direction-confirmed-by:, or when 00-index.md records progress.design: skipped with a reason.

What later stages do with the design

  • slice maps every slice to the surfaces in 02c-craft.md.
  • plan does not write 02c-craft.md. It reads the contract, turns every item of the mock fidelity inventory into a plan step, and writes ## Design Components: the system components that the slice uses, and the new or changed components.
  • implement builds from the tokens and components in DESIGN.md and records the result in ## Visual Contract Honored.
  • verify measures the design floor. When the stack can capture the running surface, verify puts each built surface next to its drawing in ## Design Comparison.
  • review judges drift from DESIGN.md and from the design direction.
  • retro writes back to the design record.

A later stage does not redraw the design. When a stage cannot build the design as drawn, it stops, sets status: awaiting-input, and routes to /wf design <slug> amend.

A pre-write hook refuses a 04-plan*.md write while the workflow needs design and the design is not settled. To turn the hook off, set hooks.designDirectionGate: false. See Configuration.

UX impact

Intake records ux-impact in 00-index.md. The value says how far the change reaches into what a person sees and does. Intake sets the value from the request and the files in scope, and the person confirms it with the stack question.

ValueThe change
noneChanges nothing that a person sees or does: no UI file, no user-facing text, no change to a flow.
visualChanges how an existing surface looks.
flowChanges what a person does or reads in sequence: steps, states, user-facing text, error handling. It adds no new surface.
new-surfaceAdds a screen, page, view, dialog, or reusable component.

When two values apply, intake records the higher one. new-surface is the highest and none is the lowest.

When the value is not none, the workflow needs design. Shape writes the brief 02b-design.md, with a ## UX intent section, and the design stage runs before slice. When the value is none, shape records progress.design: skipped and a one-line reason, and the workflow goes from shape to slice.

The change-modes (fix, refactor, hotfix) also set ux-impact. When design is needed, the person is present, so intake runs a compressed design stage before it writes 03-slice.md: a short brief, one drawing per changed surface, one confirmation, then 02c-craft.md.

The command grammar

The /wf design key has five forms:

/wf design <slug> [move] [instructions]      Run the design stage: draw, confirm, write 02c-craft.md.
/wf design <slug> amend [instructions]       Reopen a confirmed design.
/wf design [slug] audit|critique             Run a design review dimension now.
/wf design <move> <instructions>             Start a new workflow seeded with a move.
/wf design setup|teach|extract|direction|sync [instructions]
                                             Maintain the project's design record.

The command resolves the first token with an exact existence check, never with fuzzy matching. When .ai/workflows/<token>/00-index.md exists, the token is a slug. Otherwise the token is the command. A wrong guess would send the work down the wrong path, so design does not suggest a near slug. An unknown token stops the run and shows the usage.

amend reopens a confirmed design. Use it when a later stage found that it cannot build the design as drawn, or when you changed your mind. Amend changes only the surfaces that the reason names, asks for your confirmation again, keeps a snapshot of the prior contract, and names every plan that cites a changed surface. Run /wf plan <slug> <slice> again for each of those plans.

The design record

The project keeps one design record across all workflows. Every workflow that needs design reads it, and the record outlives every workflow.

PartFileHolds
IdentityPRODUCT.md (project root)Users, register, voice, anti-references, principles
SystemDESIGN.md (project root)Tokens, components, patterns, elevation
Current design.ai/design/current.mdThe surfaces that exist, their drift from the system, and the design debt
Direction.ai/design/direction.mdDesign goals, the future direction, open and decided design questions

Five upkeep commands maintain the record. They write the record only and touch no workflow artifact:

  • setup writes PRODUCT.md and DESIGN.md, then both .ai/design/ files, from one discovery round with you. When a file exists, setup updates it and keeps its content.
  • teach asks you questions and updates any of the four parts that your answers touch.
  • extract reads the tokens and component patterns that the code already uses and writes them into current.md. It changes no code. It is a good first command on a codebase whose visual language was never written down. With a slug, it also writes its report under the design-notes/ folder of that workflow.
  • direction shows you the goals, the future direction, and the open decisions, asks what changed, and writes only what you confirm.
  • sync keeps DESIGN.md and the design system of the host in step, one component at a time, after you approve the plan. When the host has no sync surface, it reports that and stops.

retro also writes back at the end of every workflow that needed design. It updates the surfaces and the design debt in current.md. It writes each proposed change to direction.md as a question for you, and it changes direction.md only after you answer.

The record files keep the [TODO] and <!-- intentionally omitted --> markers, so a gap is visible and is never filled with an invented goal.

Moves

A move is a design playbook. It is not a stage and it is not a separate lifecycle. There are 15 moves:

MoveWhat it focuses on
adaptContext adaptation: responsive, platform, theme, print
animatePurposeful motion and micro-interactions
bolderVisual presence and hierarchy
clarifyLess cognitive load and better scannability
colorizeStrategic use of color
delightMoments of joy and personality
distillRemoval of complexity down to the essential core
hardenAccessibility and robustness
layoutSpatial structure, grid, and alignment
onboardEmpty states and the first-run experience
optimizePerformance, with profiling before optimizing
overdriveTechnically extraordinary visual effects
polishFinishing details and state completeness
quieterLess noise and visual complexity
typesetTypography quality and hierarchy

Use a move in one of two ways:

  • With a slug, /wf design <slug> <move> runs the design stage focused on that move. The move focuses the contract. It does not widen the scope of 02-shape.md.
  • Without a slug, /wf design <move> <instructions> starts a new workflow. It runs intake with your instructions and records the move and a ux-impact of at least visual. You confirm ux-impact in intake. The workflow then runs shape, and the design stage focuses on the recorded move.
/wf design <slug> typeset tighten the heading scale on the dashboard
/wf design polish tighten the settings page hierarchy

Plan cites the moves as step pointers. Implement applies them and records what changed in design-notes/<move>-<timestamp>.md.

audit and critique

Two commands review the work instead of building it. They run the same logic as the design-audit and design-critique dimensions of /wf review, on demand:

  • audit is a technical quality scan with 0–4 scoring. It covers accessibility, performance, theming, responsive behavior, and anti-patterns. When the workflow has verify results, audit uses the measurements in 06-verify-*.md. It measures for itself only when no verify ran.
  • critique gives prescriptive design feedback. The stance of the feedback follows the register: brand work is judged on distinctiveness, and product work is judged on earned familiarity.

With a slug, the commands write 07-design-audit.md or 07-design-critique.md in the workflow and register themselves in 00-index.md. Without a slug, they write no workflow artifact and report in chat.

The canvas and its fallbacks

The design stage draws on the best surface that the host offers:

  1. The design canvas. When the host has a design canvas (under Claude Code, a Claude Design artifact), the stage draws one artboard per surface and state, with the tokens and components in DESIGN.md. It records the canvas link as canvas: in 02c-craft.md.
  2. Generated comps. When the host has no design canvas, the stage uses the imagery skill to generate one to three north-star comps.
  3. An interactive prototype. When you want an interactive prototype of the approved direction, the stage offers the uiproto skill. It never runs it automatically. uiproto needs externalDispatch.enabled. Without that flag, imagery uses only its no-egress paths. See Skills.

For a flow change where no surface changes how it looks, a text flow is valid. The contract then records image-gate: skipped:<reason>.

The Register line and the image gate

Every design run reports two lines in its closing summary.

Register: brand | product. Brand work is a surface where distinctiveness wins, for example a marketing page. Product work is a surface that people use daily, and it is judged on earned familiarity and restraint. The register changes the stance of the design and of critique.

Image gate: pass | skipped:<reason> | n/a. The image gate stays pending until the design stage resolves it to pass or to a skip with a reason. A pending gate means that the design is not settled. Commands that draw nothing (audit, critique, and the upkeep commands) report n/a.

What drivers do

Drivers never decide a design:

  • /wf auto pauses at the design stage when design is needed and not settled. It routes you to /wf design <slug>. After you confirm the design, run /wf auto <slug> again.
  • /wf yolo refuses to start while design is needed and not settled. It drives from plan onward only.
  • When a driven stage cannot build the design as drawn, the run stops and routes you to /wf design <slug> amend.

To let a driver build a UI change, run intake and shape, confirm the design with /wf design <slug>, and then start the driver.
