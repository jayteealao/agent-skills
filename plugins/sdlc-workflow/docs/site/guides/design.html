Design

This page shows how to use /wf design, one command that hosts twenty design operations, from "make this bolder" to a full accessibility audit. Design work attaches to a workflow that you already have, or it roots a whole new lifecycle.

The grammar

Everything runs through a single shape:

/wf design [slug] <command> [instructions]

The first token after design is an optional slug. The command resolves the token with an exact existence check, never with fuzzy matching. If .ai/workflows/<token>/00-index.md exists, the token is a slug, and the next token is the design command. If that file does not exist, the first token is the design command. A wrong slug guess would send the work down the wrong flow entirely. For that reason, design deliberately skips the fuzzy slug suggestion that other stages use. Everything after the command is free-text instruction for the command.

The twenty design commands are arguments to this one key. No design command is its own /wf key. The commands fall into four categories, and the category decides how far the run travels.

The 15 transformation verbs

Transformations are the commands that produce or modify code. Each transformation is a verb that names one design move:

What a transform run actually produces

A transform is not a one-shot code edit. It runs a condensed but complete span of the normal lifecycle. It emits every numbered artifact along the way, so the rendered views and downstream checks see an ordinary workflow:

  1. A focused visual contract (02c-craft.md), scoped to the transform's one move. For colorize, that move is the color strategy. For typeset, it is the type scale. The contract step resolves the image gate before any code changes.
  2. slice — a single thin slice, unless the surface inventory clearly demands more.
  3. plan — a per-slice plan that cites the design references as concrete step pointers.
  4. implement — the transform itself is the implement step. Each applied design reference is registered as a design add-on in 00-index.md. A design-notes/<verb>-<timestamp>.md record documents what changed, why it changed, and which reference guided the change.
  5. verify — the measurable design floor: accessibility, performance, and responsive checks, plus a re-check of each applied add-on.

A transform owns this whole span. It does not write the contract and then hand back. The flow builds code at its own implement step, so you can run a transform against a surface that does not exist yet. The transform either creates the surface or modifies the workflow's existing implementation. "There is nothing to transform" is not a blocker.

audit and critique

Two commands review the work instead of building it. Neither command runs a slice, plan, or implement span:

  • audit writes 07-design-audit.md, a technical quality scan with 0–4 scoring. The scan covers accessibility, performance, theming, responsive behavior, and anti-patterns. When the workflow already has verification results, audit consumes the measurements from 06-verify-*.md and does not measure again. Audit measures for itself only on an ad-hoc run where no verification exists.
  • critique writes 07-design-critique.md, prescriptive design feedback. The stance of the feedback forks on the Register (see below): brand work is judged on distinctiveness, and product work is judged on earned familiarity.

Both commands are also available as dimensions inside the fan-out of /wf review. A standalone run here uses the same logic. Both commands register themselves as add-ons in 00-index.md, so later stages can see that a design review happened.

extract

extract is the read-only command. It reverse-engineers the design tokens that are already implicit in existing code. It writes design-notes/extract-<timestamp>.md plus design-notes/tokens-extracted.css. It changes nothing and needs no prior context; that trait defines it. That trait also makes it the right first command on a codebase whose visual language was never written down.

setup and teach — the project's design memory

setup authors two files at the project root, not inside any workflow: PRODUCT.md (what the product is and who it serves) and DESIGN.md (the visual language). teach updates and improves those same files as the project's design understanding deepens. The two commands behave identically with or without a slug, because the two files are shared across every feature. Every later design run reads the two files as context. Both commands preserve the [TODO] and <!-- intentionally omitted --> conventions, so gaps are explicit, not silently absent.

The Register line and the image gate

Every design run reports two lines in its closing summary. These two lines are the load-bearing signals of the whole system.

Register: brand | product. The register says which of two design modes the work is in. Brand work is a surface where distinctiveness wins, for example a marketing page or a hero moment. Brand work is judged on how memorable it is. Product work is a surface that people use daily. Product work is judged on earned familiarity and restraint. The same critique and the same transform land differently in each register. For that reason, the register forks the stance of critique, and the register is stamped on every transform's artifact record.

Image gate: pass | skipped:<reason> | n/a. The image gate is a mutation lock. The gate stays pending, and it blocks any code change, until the contract step resolves it to pass or to an explicitly reasoned skip. Commands that do not mutate code (audit, critique, extract, setup, teach) report n/a. The point is that no transform rewrites your UI before the visual intent is pinned down and checked.

Attaching to a workflow vs. rooting a lifecycle

The optional slug decides how big the run is.

With a slug, design work attaches to the existing workflow. Use it to improve a surface that an in-flight workflow owns, with extra instruction if you want it:

/wf design <slug> typeset tighten the dashboard's heading scale

A transform runs the condensed span described above inside that workflow's directory: focused contract, slice, plan, implement, verify. It advances the workflow's own bookkeeping as it goes. audit and critique write their reports into the same workflow. The notes from extract land in the workflow's design-notes/.

Without a slug, a transform has no workflow to attach to, so it creates one. It then runs the full lifecycle, from intake through shape, slice, plan, implement, verify, review, handoff, ship, and retro, seeded by the design intent. In that flow, the shape stage authors the design brief (02b-design.md), and the plan stage authors the full visual contract (02c-craft.md), exactly as for any visually-surfaced feature. The interview starts from the transform's intent. The review and analysis commands, run without a slug, produce standalone one-shot reports instead.

The design brief and the full visual contract are always authored by the normal lifecycle: shape writes the brief, and plan writes the contract. A transform authors only a focused contract scoped to its single move. There is no separate "author me a design brief" command here. UI work that needs the full brief-plus-contract treatment flows through shape and plan like everything else.
