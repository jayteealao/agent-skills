    sdlc-workflow · user reference

    Every /wf command, on one page

    One command runs the whole software lifecycle, from a rough idea to a shipped release and its retro. Find your situation below, copy the command, and fill in the parts in <angle brackets>. Each run writes its record into .ai/workflows/<slug>/ and ends with the exact next command.

    • 18 keys
    • 6 sub-keys
    • 17 intake modes
    • 11 review rubrics
    • 3 hosts

    01I want to…

    Pick the sentence closest to your situation. Each one jumps to its command. When nothing fits, type /wf and describe the work in your own words. /wf names the command that it would run, and runs it after your yes.

    02How a command reads

    The first word after the prefix is usually one of the 18 keys. The second word can be a sub-key or an intake mode. Everything else passes to the key unchanged. There are no flags to learn: position carries meaning. Words that do not fit a key go to the router, which turns them into one command.

    /wfhost prefix intakekey reports-exportslug fixmode date column shows epoch millisdescription
    /wfhost prefix loopkey goalsub-key reports-exportslug
    • The slug names one workflowIntake picks it from your description. Every later command takes it, and /wf status lists them all. A slug alone, /wf <slug>, runs the next step of that workflow.
    • A merged branch asks to closeWhen the branch of an open workflow is merged, the next /wf call asks whether to close that workflow. A no is not asked again.
    • The first call sets up the repoIn a repo with no .ai/ folder, the first /wf call asks what the repo is and which commands test it. Then it reports the merge method of GitHub and what ship still needs, and runs your command.
    • Your workflows on GitHubWhen the records repo is set up, each workflow has an issue there, and one board shows them all. Each state change updates the issue, and a needs-me label marks the work that waits on you. Answer in the session, not on GitHub.
    • Continue on any computerA repo linked to the records repo keeps its records there. Each step is committed and pushed, and each /wf call pulls the work of your other computers. One computer writes a workflow at a time; to move, release the lease with wf.mjs lease release. Computers and projects leave each other messages with wf.mjs msg.
    • The model asks onceThe agent may start /wf on its own only after you said yes once, for that workflow or for its list. Your answer to the question is the record of the consent.
    • Six sub-keysloop goal · optimize · prototype, status recap, project ship-plan · observability. A bare /wf loop or /wf project asks which one.
    • A bare /wf asks/wf alone asks what you want to do: continue one of your three newest open workflows, ask a question about /wf, or show all keys.
    • Plain words are routedWords that do not fit a key go to the router, for example /wf keep going on export or a misspelled key. It names one command and asks first. A request for new work goes straight to intake. A question such as "how do I ship a hotfix" gets an answer and the command.
    • Every run ends the same wayA status line, a short story of what happened, an Artifacts: line, and one Next: command.

    03The lifecycle

    Nine stages in order. Each stage writes its section of the workflow's records, named under each command. Run each one yourself, or let a driver run the middle stretch.

    04Intake modes

    Intake is the front door. Its modes are other ways work comes in. A mode word right after intake starts that mode. A slug first means the run acts on that workflow.

    How intake reads its words checked in this order

    1. <mode> <packet-slug> · a packet pathA work packet. An investigate, discover, rca or task packet runs that mode. A build packet is refused: /wf campaign <source-slug> builds it.
    2. <slug> amend · modernize · closeMaintenance. Edits, backfills or closes that workflow.
    3. <slug> <mode> …Compressed slice. The mode runs as one slice on that workflow. No new branch.
    4. <slug> <anything else>Extension. Adds full new slices to that workflow.
    5. <mode> …Standalone mode. Starts a new workflow of that kind.
    6. <description>Default flow. When the words strongly match one mode, intake proposes it once and asks.

    To force the default flow when your description starts with a mode word, quote it as one token: /wf intake "fix is a strong word for this". A first word close without a slug is a description ("close the dropdown on escape").

    05Drivers and loops

    Commands that check built work at runtime, run stages for you, or repeat one kind of round until a script says the work is done.

    Design, step by step

    The design stage runs between intake and slice when the work changes what a person sees. You approve every changed screen before any driver runs, so yolo and the campaign never decide a design. The screens are HTML pages with mock data on the design surface of the repo, .ai/design/, and git tracks them. Start or resume the stage with /wf design <slug>.

    CommandDoes
    /wf design <slug>Runs the stage: draws each changed screen, checks it, and records your approval.

    The flow a driver never runs this stage

    1. 1Orientagent

      Stops when a driver called it or the shape is not complete. When ux-impact is none, asks whether to design or to skip.

    2. 2Read the recordagent

      Reads PRODUCT.md, DESIGN.md, the current design and the direction. Every reference must be a file that an agent can read.

    3. 3Carried thoughtsyou

      Shows what a design brainstorm or an explore run left, and asks only about contradictions and open questions.

    4. 4Inspectagent

      Four sub-agents read the code. When the product runs, each touched surface is captured as it is now.

    5. 5The formyou

      One question: the whole feature, three directions first, a flow of states, or changes to existing screens.

    6. 6Directionsyou, when open

      Three named directions on different axes, plus the category standard. You pick one, mix two, or ask for another round.

    7. 7Drawagent

      Every changed screen of the whole feature, in five states: default, empty, loading, error and worst. Each step of a flow is a link.

    8. 8Roundsyou

      Three to five decisions per round, with numbered options, until no decision is open. The canvas comments feed each round.

    9. 9Check and approveyou

      The check runs. You answer Approve, Adjust or Stop, with each failure in view.

    10. 10Recordscript

      Commits the screens, keeps one picture of each, writes the visual contract, and updates the tokens in DESIGN.md.

    Checks and approval only your answer approves

    • The checkwf.mjs design check tests contrast, target size, viewport fit and worst-case content of each screen, in each viewport and state. Each failure names its fix: colorize, adapt, layout or harden.
    • ApproveA script reads your answer to the approval question, commits the screens in the product repo, and writes the approval commit into the contract. Agreement in free chat is not an approval.
    • AdjustThe agent changes the screens that you name, runs the check again, and asks again. Each adjustment is a recorded decision.
    • StopThe contract stays unwritten, and the workflow waits for you.
    • The settled ruleA contract that names screens is settled only when a script recorded the approval and every screen page exists. Slice, yolo and the campaign stop until then.
    • You always see the screensA confirmed PRODUCT.md or an earlier teach answer never replaces the approval.

    After the approval each later stage uses the screen keys

    StageWhat it does with the screens
    sliceWrites the screen keys of each slice into its scope and its own ux-impact. The canvas shows a design card for each slice.
    planCites the screen keys in the steps that build each screen.
    implementReads each screen page at the approval commit. It makes the worst-case content loadable in development, never in production code.
    verifyCaptures each built screen, and its worst state, beside its approved picture, and lists the differences.
    retroNames the screen keys of each surface in .ai/design/current.md.

    The canvas and the design server review from the phone

    The canvas shows every screen of a repo on one board, in each viewport and state, with the check failures, the comment threads, the flows, the history and a card for each slice. One design server per computer serves the canvas of every registered repo, on 127.0.0.1 and on the tailnet address. The server writes two things only: a comment on a screen that exists, and the positions that you drag. In the commands, wf.mjs is node <plugin>/scripts/wf.mjs.

    CommandDoes
    wf.mjs design server startStarts the server in the background.
    wf.mjs design server urlPrints its addresses. On the phone, open /r/<repo>/?workflow=<slug> on the tailnet address.
    wf.mjs design server statusTells whether the server runs and whether the logon task is installed.
    wf.mjs design server install · uninstallAdds or removes one Windows scheduled task that starts the server at logon. After a plugin update, run install again.
    wf.mjs design publish <root>Writes one self-contained canvas page, with no comments and no layout saves, for a reviewer who cannot reach the server.
    wf.mjs design comments <root>Prints the open comment threads. The agent reads them before each round.
    wf.mjs design viewports <root> [name=WxH…]Shows or sets the viewports. The defaults are phone 375×812, tablet 768×1024 and desktop 1280×800.

    Older boards once per repo

    A workflow from before the design surface keeps its boards in .ai/workflows/<slug>/design/. Run wf.mjs design migrate <root> --check first. It lists each workflow, its revisions, the confirmed revision and the screen key of each board, and it writes nothing. Then run wf.mjs design migrate <root>. It must exit 0. The boards of one surface and state become one screen, and each viewport stays a page of that screen. Each revision becomes one commit, and a confirmed revision counts as an approval. .ai/design/migrated.json maps each board key to its screen key, and the old board files stay.

    Files in .ai/design/ of the product repo

    FileWhat you find there
    screens/<key>.htmlOne screen: an interactive page with mock data and the five states. ?state=<name> shows one state.
    explore/<key>.htmlA sketch of an explore run or a direction. It is not a screen.
    tokens.cssThe token sheet, made from the token roles of DESIGN.md.
    screens.json · layout.json · references.jsonThe manifest, the canvas positions and the references. Only the scripts and the canvas write them.
    current.md · direction.mdThe design record: the current design and where it goes next.
    design.yamlIn the workflow folder: the design brief, the visual contract with its screen keys and approval commit, and the design checks.

    The comments, the approval pictures and the check results are kept in the records, not in .ai/design/, because a product repo can be public.

    Brainstorm, step by step

    A thinking partner for a half-formed idea. You lead. The agent maps the areas the idea touches, goes wide before it goes deep, brings ideas of its own, and keeps a board of everything said. It never commits: a choice that other work would build on, such as a data format, becomes a question for the plan. Only you end a brainstorm.

    Ways to start

    CommandDoes
    /wf intake brainstorm <idea>Opens a new board on the idea.
    /wf intake brainstorm <brainstorm-slug>Resumes the board. It opens with the story of the last sitting, and never asks again what the board answers.
    /wf intake brainstorm design <idea>A new board with the design focus: how the idea looks and behaves.
    /wf intake brainstorm <brainstorm-slug> designSwitches an open board to the design focus.
    /wf intake brainstorm <brainstorm-slug> add <text>Quick capture: one new piece of work, for example a bug you found while trying built work, written as a packet.
    /wf intake <slug> brainstorm design [idea]Brainstorms the design of an existing workflow. At done it routes to design <slug>, or design <slug> amend when the design is already confirmed.
    /wf intake <slug> brainstorm <topic>A brainstorm as one compressed slice on an existing workflow. The agreed pieces become a later extension.

    The flow

    1. 1Open the boardagent

      Maps the areas the idea touches and asks the first batch.

    2. 2The loopyou lead

      Batches of one to four questions, talk turns, and your replies. No floor, no cap.

    3. 3Check inyou

      At natural moments: a short summary you correct, and where to go next.

    4. 4Close an areayou

      Its price, the core items, the first version, and the risk that worries you most.

    5. 5doneyou

      Scope the work now, or keep the board and think more later.

    6. 6Walk the discussionyou

      Area by area: keep, cut, leave for later, or change each item.

    7. 7Shape the workyou

      Group kept items into pieces, put them in order with a reason, pick each form.

    8. 8Confirmyou

      Nothing is written before you confirm. Then the packets are written, and document-only pieces are done in the session.

    Each turn one topic per batch, in plain words

    QuestionWhat it does
    reflection"I heard: …" with two to four readings of your last thought.
    probeTests one assumption or one gap, with the agent's best guesses as options.
    forkDirections the thought can take next. You can pick several.
    widenA direction you have not raised, with the agent's own ideas.
    choiceOptions that exclude each other: an order, a trade-off or a cut, each with its cost.
    talk turnWhen the ground is new to you, the agent explains in chat with an example and its own view, and ends with an invitation, not a question.

    Every question says what is known and why it matters before it asks. When you set a risk aside or take the costliest option, the agent states the consequence once and records the risk you accept. Paste a brief or name a file, and the agent maps each of its criteria as covered, partial or open.

    Control words the first word of a free-text reply

    SayEffect
    park <thread> · pull <thread>Stop asking about a thread, or bring it back. Name the thread in words.
    drop <thread>Drop a thread, with your one-line reason.
    boardShow where we are: summary, areas, live threads, open tensions, top risks. No question this time.
    look it upSends one research agent on the last unchecked statement. The result is saved as a research note.
    second opinionAsks another model which assumptions and tensions the thinking missed. Never runs unasked.
    cohereChecks the board against itself, against work it already routed, and against your budgets.
    pauseThe story of this sitting: what we explored, learned and decided, what is open, where we start next. The board stays open.
    doneEnds the loop and starts scoping the work with you.

    Check-ins and closing an area

    • A check-inComes when a thread feels settled, the answers get short, the direction changes a lot, or the agent thinks the thinking is complete. You correct the summary, then choose: go deeper, open a new area, zoom out, show where we are, or stop for now.
    • Closing an areaThe agent writes a brief of five lines or fewer and shows the area's price against your budgets. You pick the core decisions, what goes in the first version (the rest waits; nothing is cut unless you say so), and the risk that worries you most.
    • Changes to started workA work packet whose workflow started is never rewritten. A new decision about it becomes a new work packet: an extension, a fix or a hotfix.

    At done each agreed part of the work gets a work packet

    FormFor
    intakeA feature to build.
    extensionNew scope on an existing workflow.
    fix · hotfixA correction to built work; hotfix when people already use it.
    rcaA defect with an unknown cause.
    investigate · discoverA problem to study first, or a yes-or-no question to check.
    taskA deliverable that is not code.
    write-nowA change to documents only. Written in the same session after you confirm.
    • One strict orderEvery work packet gets a place, 1 to n, and each one after the first gets a reason for its place. The campaign builds them in that order, one at a time.
    • Confirmed onceFor each build packet you confirm the goal, the scope, the acceptance criteria, ux-impact and try-out, and the stack once for the list. The campaign does not ask again.
    • What a packet carriesYour decisions word for word with their dates, the findings, the open questions, the sources, and the start command.
    • ThenWith any build packet: /wf campaign <slug>. A packet of another form prints its own command, for example /wf intake investigate <packet-slug>.
    • Designdesign and design-direction are not forms. A design focus marks a packet with one of them, so the campaign stops for the design stage.
    • A page for each brainstormAfter each check-in, at a pause and at the end, an agent updates one page that shows the map, the threads, every decision and the work packets, in light and dark.
    • The board stays openResume it at any time. Retire it with /wf intake <slug> close when no thread is live.

    Design focus sketches are ideas

    The design focus reads the design record (PRODUCT.md, DESIGN.md, the current design and the direction) and maps the design space: surfaces, what a person does on each, layout, color and type, motion, states such as empty, loading and error, and voice. The agent sketches when a picture decides faster than words, as an explore sketch on the design surface, .ai/design/explore/. You see the sketches on the canvas and pick one by its number, or a mix. A brainstorm never confirms a design: the design stage does. At done, each work packet carries its design items, a proposed ux-impact and its sketches to the design stage, which presents them again as its starting direction.

    Rules that protect you

    • Only you end itThe agent never decides that the thinking is complete. When it thinks so, it checks in and continues.
    • Plain wordsNo board key, internal number or mode name appears in anything you read.
    • Nothing becomes work without youNo packet is written until you confirm the scope.
    • The board is the memoryBoth files are rewritten after every batch, so a lost session loses at most one batch.
    • Bounded evidenceA checkable statement gets one short read of the code, cited as file:line. Research agents run only on look it up.
    • Started packets stayA packet whose workflow started is never rewritten. A new decision about it becomes a new packet, and a cut of started work is a question to you.

    Ideate, step by step

    Ideate finds work you did not ask for. Agents scan the code through six lenses, generate candidates with evidence, cull the weak ones, and rank the rest. Name sources and a seventh lens matches each item of each source to your code. Ideate reads only and writes no code. Then you go through the ideas with the agent: take, keep for later or drop each one, talk one through, or send the scan deeper or in a new direction in the same run.

    1. 1Orientagent

      Reads active workflows, retro action items, deferred review findings, sdlc-debt markers and earlier ideate runs.

    2. 2Sourcesagent

      Reads each source into references/ and lists its items.

    6. 6Rankagent

      One work packet per idea. The workflow closes and prints the start commands.

    Lenses

    LensFilter wordLooks for
    1 · Code quality and debtqualityComplexity and churn hotspots, untested files, TODO and dead code, duplicated logic, outdated patterns.
    2 · Performance and scaleperformanceN+1 queries, missing pagination and indexes, caching gaps, heavy loops, blocking work. Each finding says why it matters at 10× load.
    3 · Security and privacysecurityUnsanitized input, missing authorization, hardcoded credentials, secrets or PII in logs, dependencies with known CVEs.
    4 · Developer experiencedxSetup steps that fail silently, poor error messages, inconsistent APIs, docs that no longer match the code.
    5 · Feature gapsfeatureMissing loading, error and empty states, accessibility gaps, acceptance criteria with no test, stubs.
    6 · ArchitecturearchitectureOversized modules, circular dependencies, missing or needless abstractions, coupling hotspots.
    7 · Source fitruns with sourcesMatches each source item to the code and to your installed version. A finding cites the source line and a file:line.

    The cull every candidate faces all challenges

    • 1 · Is it real?A speculative finding is culled. When its impact would be high if true, it is kept as needs-verification with the cheapest check named, such as a discover or a probe.
    • 2 · Is it already in progress?Work that an active workflow does, or just shipped, is culled.
    • 3 · Is the effort justified?Large effort for small impact is culled.
    • 4 · Is it specific enough?"Improve the architecture" fails. It must be ready for intake as it is.
    • 5 · Is it the right level?Two symptoms of one cause merge into the root cause.
    • 6 · Is it stable and available?Sources only: the feature must exist in a version you can use.

    Ideate remembers earlier runs. An idea an earlier run culled stays culled until its evidence changes: a cited file changed, or a new source item supports it. An idea already picked counts as in progress.

    06Campaign, step by step

    Use a campaign when a brainstorm or an ideate pick wrote a list of work packets. The campaign is a walk: it goes down the list in order, one work packet at a time, on one branch, packets/<slug>. Each work packet is a normal workflow. When the list is done, you hand off one PR for the whole list. Start or resume the walk with /wf campaign <slug>, where the slug is the brainstorm or ideate workflow that holds work/index.md.

    A work packet one agreed part of the work

    • Where it comes fromAt done, a brainstorm writes one work packet for each agreed part of the work. An ideate pick writes one for each picked idea. The list, work/index.md, holds them in one strict order, and each place after the first has a reason.
    • What it carriesYour decisions word for word, with their dates. Also the findings, the open questions, the sources, the form, ux-impact, try-out and its state.
    • A key and a slugThe key is the name on the board. The slug names the workflow folder of the work packet. Each campaign command takes the key, and also accepts the slug.
    • One workflowThe walk opens each build packet as a normal workflow, .ai/workflows/<packet-slug>/, with its intake and shape written word for word from the work packet.
    • Started work staysA work packet whose workflow started is never rewritten. A new decision about it becomes a new work packet.
    StateMeans
    writtenThe brainstorm or the ideate pick wrote the work packet. No workflow exists yet.
    openThe walk opened its workflow. Design, slice and the driver run from here.
    builtThe driver reached its endpoint, and the work is pushed. Fidelity and the try-out come next.
    doneEach fidelity row is approved, the try-out is recorded, and the trunk is merged in.
    droppedYou dropped the work packet. The walk continues with the next one.

    Before you start

    • A listA brainstorm that reached done, or an ideate pick, wrote work/index.md and one work/<packet>.md per work packet. With no slug, the campaign lists the folders that hold a list and asks which.
    • A confirmed scopeYou confirmed the goal, the scope, the acceptance criteria, ux-impact, try-out and the stack at done. The campaign does not ask about them again.
    • One branchEvery work packet lands on packets/<slug>. The campaign never stashes and never forces. When git refuses the switch, it shows the files in the way and asks.
    • Design in this checkoutYou can design a later work packet between two work packets, in this checkout, on the list branch. Design work in another worktree or on another branch does not reach the campaign.
    • A ship planRun /wf project ship-plan init before ship. At the start, the walk lists each ship gap as a task for you. It stops on a gap only at ship.

    Each form the campaign builds only the build forms

    FormWhat the campaign does
    intake · extension · fix · hotfixBuilds it: open, design when needed, slice, drive, fidelity, try-out, done.
    investigate · discover · rca · taskStops and prints its command, for example /wf intake investigate <packet-slug>. When that workflow is complete or closed, the work packet is done.
    any formWhen you drop a work packet, the campaign marks it dropped and continues with the next one.

    How the walk slices a work packet one slice per capability

    • A slice is one capabilityA capability is a group of mechanisms that verify checks together, for example "the staff attribute model and ratings". The small outcomes of the capability become the steps of its plan.
    • The sizeA slice has fewer than 40 plan steps. A larger capability becomes two slices. Lines of code do not set the size.
    • About 10 slicesThe walk aims for 10 slices per work packet. Above 14, it writes them and tells you the count. You can split the work packet later.
    • One reviewThe review covers the whole work packet, once. A fix slice runs that review again.
    • ScreensWhen the work packet has approved screens, each slice names its screen keys and its own ux-impact.
    • Your scope staysThe walk does not ask about the scope, the criteria or the stack again. A slice that drops or narrows an acceptance criterion is a question to you.
    • Your own slicesWhen you ran /wf slice <packet-slug> yourself, the walk keeps your slices and skips this step.

    Each stop the campaign asks; it never guesses past a stop

    StopWhat you do
    design not settledType /wf design <packet-slug>. For a design-direction packet, type /wf design direction from <slug> first. Then run the campaign again.
    yolo stoppedThe campaign shows the stop and follows your answer, then resumes the driver. It does not go to the next work packet.
    a fidelity rowUp to four rows per question, each with the decision word for word, the verdict and the evidence. Approve it, or fix it. An approval goes into the packet's decisions.yaml.
    the try-outThe campaign tells you how to run the work packet and lists each acceptance criterion. Say that it works, or describe the problem.
    a merge conflictResolve the conflict by hand, then run the campaign again.
    • A problem becomes a new sliceA fix runs /wf intake <packet-slug> <problem>, which adds a slice to the work packet. yolo builds the slice, and the review runs again over the whole work packet.
    • New scope becomes a new work packetWhen the problem is new scope, add it to the list with /wf intake brainstorm <slug> add <text>. A fix or a hotfix goes before the first work packet that is not sliced; any other form goes last.

    Handoff and ship one PR for the list

    • When the list is doneEach work packet is done or dropped, and no fidelity row waits for your approval. Type /wf ship packets/<slug>. The PR lists each work packet with its acceptance results and its decision fidelity table.
    • Then ship and retro/wf ship packets/<slug> ships the PR as usual. /wf retro packets/<slug> runs one retro over every work packet on the list branch.
    • An early PRYou can ship between work packets. The PR then holds the done work packets only. After it merges, the campaign asks whether to delete the list branch and the end branches, and starts the next PR from the trunk.
    • A draft PR from the first buildThe first work packet that reaches built opens the PR of the list as a draft. Each later build pushes to it, so CI runs at the end of each work packet. Ship writes the real title and body, and marks the PR ready.
    • Stacked PRsWhen .ai/ship-plan.md has pr-shape: stacked, each build packet is one layer of a gh-stack stack, with one PR per layer. Ship each layer bottom first, or merge the whole stack at once.
    • A stack is rewrittenCAUTION: do not commit to a layer from another checkout while the walk runs. Each sync rebases the layers, so that commit diverges from the rewritten layer.
    • Deletes wait for youWARNING: the campaign deletes no remote branch, tag or release without your yes. These deletions cannot be undone.

    An old campaign migrated on the first call

    A folder that holds a ledger of the old wave campaign is migrated the first time you run /wf campaign <slug>. The campaign writes a report to work/migration.md and shows it to you. Shipped units become done work packets. Units in flight become open work packets, first in the list, and their records come home to the main checkout. You regroup the units that did not start into work packets. The old ledger moves to work/archive/campaign/, and the old worktrees are removed with a guarded remove. An old wave run that is live must stop first, and an open wave PR must merge first.

    loop optimize change the code, measure one number, keep or revert

    1. 1Specyou

      intake optimize: objective, metric command, direction, guard command, then allowed paths, budget and a holdout.

    2. 2Prove the commandsagent

      The metric's last line must parse as a number. The guard must exit 0.

    3. 3Confirmyou

      You confirm the whole spec. The metric choice is the largest risk.

    4. 4Baselinescript

      Runs the metric several times. Half the spread is the noise floor.

    5. 5Trialsautonomous

      One hypothesis per trial, in a separate worktree. The script measures and keeps or reverts.

    6. 6Branch roundsautonomous

      The best code forks into 4 branches that see only their own history. The best branch wins.

    7. 7Finishscript

      Kept trials squash into one commit on the slug branch, as one slice.

    8. 8The tailyou

      verify <slug> optimize, review with a metric-gaming check, ship, retro.

    • The keep ruleA trial is kept only when its gain is larger than both the minimum gain and twice the noise, and a confirm run agrees.
    • The script decidesoptimize.mjs makes every git write, measurement, keep and revert. The agent only proposes and edits.
    • Your tree stays yoursTrials run in one separate worktree on the trunk optimize/<slug>. Measurement is serial, so runs do not disturb each other.
    • The spec is fencedA trial that touches the metric, the guard, the holdout or their files is rejected before it is measured. The proposer never sees the holdout's output.
    • When it stops earlyYou choose: raise the budget and continue, finish with what was kept, or start a new optimize slug.

    researchFind ways to answer the question: ranked candidate proofs.
    proveProve a step: runs, measurements, one proof card per question.

    09What gets written where

    Each workflow is a folder, .ai/workflows/<slug>/. Its records are YAML files that scripts write: state.yaml and meta.yaml hold the index, intake.yaml the brief and the shape, one slice-<slice>.yaml the slice, plan, implement and verify of each slice, and design.yaml, review-<slice>.yaml, ship.yaml and retro.yaml the rest. A record file holds sections, and each section keeps the name of its old Markdown file: 02-shape.md is the shape section of intake.yaml. The command entries write a section as intake.yaml#shape. Print a section with wf.mjs record get <root> <slug> <name>, where the name is the old file name. A workflow of the old layout moves file by file at its first write, and redirects.yaml names the new place of each old path.

    10Rules to know

    The behaviors that surprise people the first time.

      Configuration

      Every option has a safe default, and every file is optional: an absent file means all defaults. Options live in four places. The repo file and the machine file share no key, so no option has two sources to reconcile.

      WhereScopeNotes
      .ai/sdlc-config.jsonOne repo. Commit it.Write checks, leak guards, policy, driver models and the yolo watch. A JSON schema rejects an unknown key. A setting that no release reads now is ignored, with one warning.
      ~/.sdlc/config.jsonOne machine. Never commit it.The records repo of this machine and the port of the design server.
      Environment variablesOne process or shellSwitches, folders, model names and credentials.
      Workflow files and markersOne workflow or one artifactdecisions.yaml, amend, and frontmatter escapes.

      Dotted keys nest in the file · .ai/sdlc-config.json

  "artifactTracking": "tracked",
  "checks": "strict",

  "design": { "port": 4711 }
