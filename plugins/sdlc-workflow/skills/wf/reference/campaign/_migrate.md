# The campaign migration (sub-procedure of campaign.md)

The walk reads this file only when `<cmd> status` gives `migrate: true` or `migrate: finish`. `<cmd>` and `<root>` are as in [../campaign.md](../campaign.md).

The source folder has an old campaign ledger (`work/campaign/ledger.json`) and no list. Its units are the old form of work packets. The person types no command for the migration.

1. Run `<cmd> migrate "<root>" <source-slug> report`. It writes `work/migration.md`. It changes no branch and deletes nothing.
2. When the result has `live: true`, stop. Tell the person that an old wave run is live, and that it must stop first.
3. When `blocked` is not empty, stop. List each wave PR of `blocked` that is not merged, and tell the person to merge it first. Otherwise the review and the PR of the first work packet include the earlier waves.
4. Show the report to the person in plain words: the shipped units, the in-flight units with their branches and uncommitted files, the units that are not started, the old worktrees, the stray folders, the steers that name another unit (`waits`), and the old stacked PRs (`prStack`). When `prStack` is set, tell the person that `pr-shape: stacked` in `.ai/ship-plan.md` keeps one PR for each work packet.
5. Run `<cmd> migrate "<root>" <source-slug> apply`. It brings the records of each in-flight unit home to the main checkout. For a linked project, home is the clone of the records repo. It makes each shipped unit a `done` work packet and each in-flight unit an `open` work packet, and it puts the in-flight work packets first, in their old unit order. It keeps a copy of the board in `work/campaign/` (`backup`). Do not copy the `.ai/` folder as a backup: it can hold gigabytes, and step 6 keeps both versions of each conflict.
6. For each entry of `records` with `conflicts`, show the person both versions: the main version, and the worktree version under `work/campaign/records/conflicts/`. Ask which version to keep, and write the kept version in the main checkout.
7. Regroup the units that are not started into work packets, with the person, in this session. For a brainstorm source, follow "Regroup" in [intake/brainstorm/_work.md](../intake/brainstorm/_work.md). For an ideate source, follow "Regroup" in [intake/ideate.md](../intake/ideate.md). The regroup confirms the whole list with the person and runs `<cmd> write`. The person can drop any work packet, an in-flight work packet too. A dropped in-flight work packet keeps its branch unmerged, and its carried decisions go back into the regroup. In every regroup:
   - **Settle each wait.** The old waves ran units side by side, and a steer of `waits` can make one unit wait for another. The walk runs one work packet at a time, in list order, and it never drives a work packet out of that order, so such a wait never clears by itself. For each wait, offer the person three answers: an order of the work packets that meets the wait, a move of the waiting slices into the other work packet, or a drop of the wait. Record the answer with `wf.mjs decide add` in each workflow that the wait names.
   - **Confirm in batches.** Show the write-ups in batches of up to four work packets. Give the goal and the acceptance criteria of each work packet in the question. Do not offer one answer that confirms more than four work packets.
   - **Split or keep.** For each work packet with an estimate above 14 slices, ask the person to split it or to keep it. The walk does not split a work packet later.
   - **Give the size.** When you confirm the whole list, give the sum of the slice estimates and the number of work packets that wait for a design.
8. Run `<cmd> migrate "<root>" <source-slug> finish`. It moves the old ledger folder to `work/archive/campaign/` and each stray folder to `work/archive/stray/`. It removes each old campaign worktree that is not the worktree of an in-flight work packet, with the guarded remove.
9. Show the person each worktree of `refused`, with its reason. The person decides what to do with it. When the entry has `ignoredAtRisk: true`, show its `ignored` files. When the person says yes, run `<cmd> remove-worktree "<root>" <source-slug> <path> --allow-ignored`.

CAUTION: do not run `git worktree remove --force` on an old campaign worktree. It deletes through a `node_modules` junction into the files that the junction points to. Remove an old worktree only with `<cmd> remove-worktree "<root>" <source-slug> <path>`.
