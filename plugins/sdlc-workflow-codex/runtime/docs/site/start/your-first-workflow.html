Your first workflow

This tutorial takes one small, real feature through the standard lifecycle, from intake to handoff. You see what each stage asks, what each stage writes, and how each stage passes work to the next.

The running example

We add a --json flag to the export command of a CLI tool. The flag makes the command emit machine-readable output alongside its existing table format. The example is deliberately small. It is big enough to exercise every stage, and small enough that you can follow the whole arc in one sitting. Everything below uses the slug export-json-flag. The slug is the stable, kebab-case name that the workflow gets at intake and keeps forever. Every artifact the lifecycle writes lands under .ai/workflows/export-json-flag/ in your repository, numbered by stage.

Each stage ends by telling you the exact next command to run, and /wf status tells you where you are at any point. You never have to memorize the sequence, but it helps to see the sequence once. That is the purpose of this page.

Stage 1 — Intake

To start the workflow, describe what you want:

/wf intake add a --json flag to the export command

Intake is deliberately not a coding step. It refuses to start solving the problem. Its job is to turn your rough sentence into a recorded brief. Intake derives the slug (export-json-flag) and checks the workflow registry for a name collision. It also fingerprints your repository: which languages, build tools, test frameworks, and platforms it detects. It writes the fingerprint down as observed fact, not guesses. Then intake interviews you with a short round of product-owner questions. For example: what the output must contain, who consumes it, and how you know that it works. Intake also asks you to confirm or correct the detected stack.

When the interview completes, intake writes two files. 00-index.md is the workflow's control file. It carries the slug, the stage tracker, and the confirmed stack fingerprint. 01-intake.md is the brief itself, with your restated request and your answers. Your answers also accumulate in po-answers.md, a running decision log that the later stages read. Finally, intake registers the slug in .ai/workflows/INDEX.md, the registry that every other command consults.

Stage 2 — Shape

Turn the brief into a mini-spec:

/wf shape export-json-flag

Shape launches research before it asks you anything. A sub-agent maps the part of the codebase that the work touches: the entry point of the export command, its callers, the existing output formatting, and the location of tests. When the work involves external APIs or dependencies, a second sub-agent checks the current state of the outside world. With that grounding, shape interviews you again, this time about scope. What is in, and what is out? Which edge cases matter? For example: what must --json do when the export is empty, or when you combine it with an existing --output flag? What are the acceptance criteria? Shape writes each criterion so that a later stage can check it objectively.

Shape writes 02-shape.md: in-scope and out-of-scope lists, acceptance criteria, and edge cases. It also writes two forward-looking plans that the later stages honor. The Documentation Plan records what docs this work owes. The add-on plan covers add-ons such as instrumentation or benchmarks. Our flag needs none of those, so shape records that decision and moves on. If the work has a visual surface, shape also authors a design brief as 02b-design.md. A CLI flag has no visual surface, so shape does not author one here.

Stage 3 — Slice

Break the shaped spec into independently shippable pieces:

/wf slice export-json-flag

Slice decomposes the spec into thin vertical slices. Each slice is a change that you can implement, verify, and review on its own. For our feature, the natural cut is two slices. The json-output slice holds the serializer and the flag wiring that makes export --json emit JSON. The edge-cases-and-help slice holds the empty-export behavior, the flag-combination rules, and the help text. Slice also asks you once to confirm the review scope: one review per slice in stage 7, or a single review across the whole workflow. For something this small, one slug-wide review is the sensible answer.

Slice writes a master index, 03-slice.md, that names every slice and the recommended first slice. It also writes one definition file per slice: 03-slice-json-output.md and 03-slice-edge-cases-and-help.md. Each definition file carries that slice's own acceptance criteria.

Stage 4 — Plan

Plan the first slice:

/wf plan export-json-flag json-output

Plan produces the concrete implementation plan for one slice: the files to touch, the ordered steps, and the verification for each step. Before it writes the plan, plan runs a reuse scan. For example, the scan asks whether the codebase already has a JSON serialization helper that the new code can call. When a step depends on a library, plan reads the library's installed source. It does not trust a remembered API. For anything non-trivial, plan also gets a free second opinion from an external model and files the critique next to the plan.

Plan writes 04-plan-json-output.md plus the 04-plan.md master. If you pass all instead of a slice name, plan plans every slice in parallel. Here we take the slices one at a time.

Stage 5 — Implement

Now write the code:

/wf implement export-json-flag json-output

Implement executes the plan. It adds the flag to the argument parser, wires the serializer, and keeps the change consistent with the conventions that the shape research mapped. This stage asks you little. The earlier stages asked the questions on purpose. Besides the diff itself, implement produces 05-implement-json-output.md. That artifact records what implement built, and where implement deviated from the plan and why. It also cross-links back to the slice definition and the plan.

Stage 6 — Verify

Check the slice against its acceptance criteria:

/wf verify export-json-flag json-output

Verify runs the project's tests, lints, and typechecks. Then verify does something stricter: it checks each acceptance criterion against observed behavior. It runs export --json and examines the output. It does not infer from the diff that the flag probably works. Captured output lands in a verify-evidence/ directory alongside the artifacts. If anything fails, verify owns exactly one fix round. Verify triages each failure with you: fix the failure now, skip the failure, or escalate back to implement. Verify applies the fixes that you approve, and re-runs only the affected checks once. Verify never loops silently.

Verify writes 06-verify-json-output.md with a pass/fail result per criterion. Then repeat the plan → implement → verify span for the second slice, edge-cases-and-help, in the same way.

Stage 7 — Review

With both slices verified, run the review:

/wf review export-json-flag

Review selects the quality dimensions relevant to this change, for example correctness, testing, and maintainability, from a much larger catalog. It dispatches one reviewer per dimension over the workflow's diff and artifacts. The findings land in 07-review.md as an accumulating ledger with an overall verdict: ship, ship-with-caveats, or dont-ship. The ledger is durable. If you fix findings and re-run review, the ledger merges in the new run, marks cleared findings resolved, and never discards history. If there are blockers, /wf implement export-json-flag reviews works through the blockers one by one.

Stage 8 — Handoff

Package the work for a pull request:

/wf handoff export-json-flag

Handoff aggregates every complete slice into a reviewer-friendly package: what changed and why, in product language rather than workflow jargon. Then handoff pushes the branch, opens the PR, and waits for CI to reach a terminal state before it declares the work ready. Handoff refuses to hand off work with unresolved review blockers. It also runs a readiness check against the project's release plan, so it never declares the PR ready against a stale release contract. It writes 08-handoff.md with the package and the readiness result.

What comes after

Two stages remain. /wf ship releases the merged work through the project's recorded release plan. /wf retro is the post-mortem that closes the loop. Shipping has enough machinery of its own (the release plan, run records, and rollback) that it gets its own guide: Releasing.

You saw the whole standard arc once. In day-to-day use, you will not always need all of it. Most small changes take the quick lane instead, which is the next tutorial.
