Everyday fixes

This tutorial shows the flow that you will use most often: a small bug fix through the quick lane. The quick lane compresses the four planning stages into a single run, then hands you to the standard execution chain.

The running example

The export command of our CLI has a bug. When the output directory does not exist, the command fails silently: no error, no file, exit code zero. The bug is small and well understood, with one obvious place to fix it. The full stage-by-stage lifecycle from the first tutorial is more ceremony than the change deserves. But you still want the recorded artifacts, the resumability, and the quality checks. The quick lane exists for exactly this case.

One command authors the whole plan

Describe the bug to the fix mode of intake:

/wf intake fix export fails silently when the output directory is missing

The important thing to understand about this mode: it compresses ceremony, never stages. Every stage of the lifecycle still happens and still writes its real artifact. The fix lane simply authors the four planning stages in one pass instead of four separate conversations. The fix lane asks you at most two questions along the way. Before it writes anything, it sends research sub-agents into the codebase to ground the plan. The sub-agents find which files the fix touches and what patterns the surrounding code uses. They also check whether a helper already exists for this task, and whether the area churned recently.

From your description, the fix lane derives a slug, here fix-export-missing-dir. It creates a branch fix/fix-export-missing-dir and writes five files into .ai/workflows/fix-export-missing-dir/:

FileWhat it holds
01-fix.mdThe brief: the restated bug, up to three objectively checkable acceptance criteria, assumptions, open questions.
02-shape.mdA tight scope: what is in, what is out, and known unknowns.
03-slice.mdA single slice. A fix is one slice by definition, and the lifecycle never skips slicing.
04-plan.mdAt most five numbered steps, each naming its files and its verification, plus the exact test commands and manual checks to run.
00-index.mdThe control file: the same full index that a standard workflow gets, with all four planning stages marked complete.

For our bug, the plan might be three steps: add a directory-existence check before the write, surface a clear error with a non-zero exit code, and add a regression test for the missing-directory path.

The gate before implement

The fix lane stops before it writes any code. It shows you the plan and asks you to choose: Proceed, Adjust, or Escalate. Adjust revises a planning artifact and asks again. Escalate restarts the change as a full /wf intake workflow, because the change turned out bigger than a fix. For a clearly low-risk change (three files or fewer, no open questions), the lane may proceed on its own. It records that decision either way.

The lane watches its own envelope while it plans. The fix can grow: more than three files, more than five steps, a new dependency, or an architectural change. The lane does not refuse; it records the breach in the plan and recommends the Escalate option at the gate. You always get a valid plan, sometimes with a record that the fix outgrew the lane.

The standard chain takes over

From here, the flow is the same execution chain as any workflow, one command per stage. Implement the plan:

/wf implement fix-export-missing-dir

Because a fix is a single-slice lifecycle, you never pass a slice name. Implement writes 05-implement.md, un-suffixed. Then check the fix against the acceptance criteria:

/wf verify fix-export-missing-dir

Verify runs the tests and the plan's manual checks against observed behavior. It runs the export into a missing directory, and confirms that the error appears and that the exit code is non-zero. Verify writes 06-verify.md. If something fails, verify triages the failures with you in a single fix round. Then run the review:

/wf review fix-export-missing-dir

Review picks the dimensions that matter for a change like this. It writes its findings and verdict to 07-review.md. The quick lane never skips review: the compression was all in planning, and the quality checks run in full. Finally, package the fix for a pull request:

/wf handoff fix-export-missing-dir

Handoff writes 08-handoff.md, pushes the branch, opens the PR, and waits for CI before it declares the work ready. This is the same as any workflow.

Attaching a fix to an existing workflow

A second form is worth knowing. Sometimes the bug belongs to a workflow that already exists. For example, you find a date-formatting bug in the export-json-flag feature from the first tutorial. In that case, put the slug before the mode:

/wf intake export-json-flag fix date fields lose the timezone in json output

Instead of a new workflow and a new branch, this form attaches one quick-lane slice to the existing workflow. It writes a single file, 03-slice-fix-date-fields-timezone.md, that contains the same researched fix plan. It updates the parent's index additively. It creates no new branch, and the parent workflow's lifecycle position does not move. The fix simply becomes one more slice of work under the slug that owns it.

When not to use the fix lane

Two neighboring modes exist for cases that look like fixes but are not. A production incident belongs in /wf intake hotfix, which branches off the production branch and runs diagnosis sub-agents. Code improvement that does not change behavior belongs in /wf intake refactor, which establishes a test baseline first. When the plan genuinely outgrows the fix envelope, take the gate's Escalate option. Do not force the change through the lane. The full lifecycle exists for exactly that case.
