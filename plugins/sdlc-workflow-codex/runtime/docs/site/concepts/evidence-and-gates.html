Evidence and gates

Read this to understand how the plugin defends itself against its own optimism. Acceptance criteria, risk ledgers, runtime evidence, deferrals, and readiness checks stop "looks done" from being treated as "is done".

An AI agent that grades its own work has a structural bias: the agent wants to report success, and the agent is very good at writing a plausible pass. The plugin's answer is not "try harder to be honest". The answer is a set of mechanical checkpoints where recorded evidence must back every claim. Each known failure shape has a named, enforced countermeasure. Examples of these failure shapes are the recalled API, the silently skipped test, and the risk that everyone forgot.

Two layers of "what done means"

The plugin defines correctness at two altitudes. Each slice carries its own acceptance criteria: concrete, user-observable statements of what that slice must do. The workflow records the criteria when it cuts the slice, and the workflow checks the criteria when it verifies the slice. Above the criteria sits the charter in 00-index.md. The charter holds durable, PO-ratified constraints that apply to every slice of the workflow, whatever the current slice is about.

The distinction matters because the two layers fail differently. A slice can satisfy all of its own criteria and still violate a cross-cutting commitment from three slices ago. For this reason, the sweep mode of /wf probe compares the running artifact against the acceptance criteria and also against the charter. When a non-functional requirement could conflict with a charter commitment, shape requires an explicit ranking between the two. An unranked conflict is an open question for the PO. The agent never resolves an unranked conflict alone.

The intent-risk (RIM) ledger: ambiguity gets a paper trail

The most expensive failures are not bugs. The most expensive failures happen when the work is built confidently on the wrong understanding of the request. The intent-risk ledger (RIM) makes sure that this failure mode cannot happen silently. At intake, each "risk if misunderstood" becomes an entry in 00-index.md under intent-risks, and each entry starts as status: open.

Shape then runs an adversarial pre-mortem in a blind sub-agent. The sub-agent sees the goal but not the draft shape, so the sub-agent cannot rationalize toward the existing answer. Any risk that the draft does not already handle becomes another open entry.

Shape must then adjudicate every entry. Either shape records a real decision (adjudicated, with the named choice and its tradeoff), or shape consciously defers the risk to a named later stage (carried). Prose that only restates the risk is explicitly illegal as an adjudication. A shape that leaves any RIM open may not declare itself complete.

The ledger also has force downstream. Handoff's readiness check treats any open RIM as not-ready. An open intent-risk means that shape never resolved a load-bearing ambiguity, and the only route forward is back through /wf shape. Carried RIMs are legal at handoff, but handoff must surface them to the PR's reviewers.

Runtime evidence, and the walls it hits

/wf verify makes one core demand: observed runtime behavior must clear each user-observable acceptance criterion. The artifact must actually run, and verify must drive it and watch it. To read the code and conclude that the code should work is not evidence. Sometimes the environment cannot produce runtime evidence: no display, no device, or a credential that nobody has. Verify calls these obstacles walls. Before a wall can excuse anything, verify must triage the wall for wall-ownership:

OwnershipMeaningCan it be deferred?
code-ownedThe wall is a defect in the workflow's own code or configuration. A change that you can write would remove the wall.No. The fix is in scope. The deferral hatch stays closed until the wall is removed.
environment-negotiableThe wall belongs to the environment, and remediation is possible: start a service, set a variable, or install a capability.Yes, after verify climbs the remediation ladder and records the residual.
externalThe wall belongs to an outside party or system that nobody in the loop controls directly.Yes, with a clearing event that names who acts.

The code-owned rule is the sharp edge. A hard-coded port, a missing headless mode, or a test that only runs on one machine is a defect in an environmental costume. Verify refuses to file these defects as environmental bad luck. Deferral is a last resort in general. Verify first climbs a constraint-resolution ladder of alternative evidence routes and records the outcome of each rung. Only the residual that no rung can reach may be deferred.

A test suite where every spec exits through a credential guard is not a wall at all. It is a procedural failure (blocked-runtime-evidence-missing) with the unmet precondition named. It is never a deferral.

Deferrals are IOUs with a named debtor

When a deferral is lawful, verify records the deferral in 00-index.md under runtime-evidence-deferrals. The schema keeps the deferral from quietly becoming permanent. Every entry carries three things:

  • The wall-ownership verdict from the triage above.
  • A clearing event that names an actor. The event is a specific act by a specific party, and the act makes the evidence producible. Passive waits, for example "once the port frees up" or "when a device becomes available", are not clearing events. A passive wait pins the deferral to state that nobody controls, so nobody is responsible for movement.
  • A clearing probe. The probe is a side-effect-free command that tests whether the wall is gone. The probe is the tripwire: /wf status and /wf probe re-run the probe. The moment the wall falls, the system notices, and the debt comes due.

The consequences depend on the stage. Review and handoff proceed past an open deferral with a warning, because in-flight work that waits on an environment should not stall mid-pipeline. But /wf ship hard-blocks until every deferral is cleared. A probe run that produces the matching evidence clears a deferral. A verify re-run in an environment that can produce the evidence also clears a deferral. A deferral is a ship-blocking IOU, and the block bites exactly where irreversibility begins.

The pass claim is checked by a machine

All of the above still depends on verify writing an honest artifact. So a mechanism that optimism cannot persuade audits the artifact itself. A PostToolUse hook inspects every verify artifact during the write. When the artifact claims result: pass while its own recorded criteria are unmet, the hook hard-blocks the write. The agent can be wrong about many things, but the agent cannot write "pass" over a body of evidence that says otherwise. The write simply fails.

The same principle runs through the whole system: the judgment and the enforcement live in different places. Verify routes, hooks block, and ledgers remember.

Readiness checks at handoff and ship

The last line of defense is the readiness check. Handoff makes work external with a PR, and ship makes work external with a release. At that point, the stage stops and evaluates whether the whole accumulated record supports the step. A readiness check is not a re-review. A readiness check is an aggregation.

Handoff's readiness check walks every slug in scope and confirms four things:

  • An implementation artifact exists for every slice.
  • No RIM is open.
  • No review verdict is dont-ship.
  • No blocker finding remains open.

The check then watches CI to a terminal state. To snapshot "pending" and declare victory is a contract violation. Last, the check computes a readiness verdict: ready, awaiting-input, or blocked. In batch mode, the verdict is a logical AND across every slug on the branch. One slug's ready never makes the PR ready while a sibling slug is blocked.

Both handoff and ship also run the shared ship-plan readiness pre-check. The pre-check asks two questions. Does .ai/ship-plan.md exist? Does the plan still describe how the code actually ships? A stale release contract is worse than none. A stale contract lends false authority at the exact moment that authority becomes irreversible: merge, tag, publish.

Each drift finding carries a tag that states what clears the finding: amend the plan, change the repo, or merge the branch. The check only offers remedies that can genuinely clear the finding. A plan amendment offered for drift that only a merge can end only costs a plan-version bump, and it returns you to the same question. The check itself never edits the plan. Like every gate in this system, the check detects and routes, and the sanctioned editor does the fixing.

One pattern runs through every gate on this page: the stage that detects a problem is never the stage that fixes the problem. Verify routes failures to implement. Handoff routes open RIMs to shape. The ship-plan check routes drift to ship-plan edit. This separation of detection and remedy keeps each record trustworthy.
