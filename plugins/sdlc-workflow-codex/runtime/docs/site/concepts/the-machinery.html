The machinery

Read this to understand what the plugin actually runs on your machine. A hub daemon serves the dashboard, and a render pipeline turns Markdown artifacts into a browsable workflow view. A tray icon watches the machinery, and hooks enforce the rules.

Most of the plugin is instructions that the model follows. But four pieces are real software on your machine: a local web server, a render pipeline that feeds the server, a small tray app that watches the server, and a handful of hooks wired into Claude Code's tool calls. When you know these four pieces, you can explain most of what you will ever observe.

The hub daemon

The hub is one long-lived, machine-wide Node process, and it listens on 127.0.0.1:4173. It reads a registry of every registered repository (~/.sdlc/registry.json), and it serves each repo's rendered workflow view at /r/<id>/. The view is the HTML under that repo's .ai/_view/.

One process and one port serve every repo on the machine: no per-repo sub-processes, no reverse proxy, no port for each repo. The hub starts automatically at session start. You can also start the hub yourself with npm run hub or from the tray menu.

Beyond the workflow views, the hub serves a few more things:

  • A landing page at the root. The landing page is the dashboard across all registered repos, and live reload refreshes the page when any repo re-renders.
  • An in-browser code browser for each repo at /r/<id>/__code/.
  • This documentation site at /docs/.
  • A health endpoint at /__sdlc/health. The tray polls the same endpoint.
  • Live reload through server-sent events. An open workflow view refreshes the moment its artifacts re-render.

Because the hub binds only to loopback, the hub exposes nothing to the network by default. Its security posture is deliberately strict for a local tool. The hub checks every request's Host header against an allowlist, which defeats DNS-rebinding. The few write and refresh endpoints under /__sdlc/ require a token. Each repo's requests are contained to that repo's own view directory, so a path traversal that escapes one repo's view cannot reach another repo's files. The hub also validates the registry entry on every read instead of trusting the entry.

The render pipeline

The plugin generates the workflow view, and nobody hand-edits the view. The pipeline from Markdown to HTML runs in three steps:

  1. A stage writes an artifact. A PostToolUse hook notices the write and enqueues a render job into a durable on-disk queue under .ai/_view/. The durable queue matters: if nothing listens right now, the job waits instead of getting lost.
  2. The hub drains the queue. The daemon picks up pending jobs and runs the render engine. The render engine walks .ai/workflows/, dispatches each artifact to a renderer for its type, and emits the HTML site under .ai/_view/. A review renders differently from a plan or a ship run. The default mode is additive: the render engine only re-renders an artifact whose sources are newer than its rendered counterpart.
  3. The browser reloads. The SSE live-reload channel tells any open view to refresh.

Rendered output can also go stale in a subtler way: the render engine itself changes, so an older engine version produced the old HTML. The hub detects this drift. The hub compares the identity stamped into rendered output against its own identity, and the hub self-heals with a bounded clean re-render. You never need to delete .ai/_view/ by hand.

The tray icon

On the desktop, a small sunflower icon in the notification area is the human-facing face of the hub. The tray app is deliberately thin: it displays state, it calls existing endpoints, and it has no other logic. You launch the tray app yourself, outside Claude entirely, with npm run tray. The tray app polls the hub's health endpoint every five seconds and shows the result in its icon and tooltip. A glance tells you whether the machinery is up.

The tray menu can:

  • open the dashboard and individual repo views,
  • refresh the registry,
  • restart or stop the hub,
  • open the hub's config and logs,
  • toggle per-repo serving,
  • register the tray app to start at login.

The hooks: the enforcement layer

The rules on these concept pages would be suggestions if nothing enforced them. The enforcement layer is a small set of hooks that the plugin registers with Claude Code, and the hooks run automatically around tool calls. The table below states what each hook does, and whether the hook blocks or acts in the background.

When it runsWhat it doesBlocks?
Session startBackground maintenance: bootstraps rendering, starts and registers the hub, and reconciles the tray on Windows.No
Session startSeeds a fenced block of /wf rules into AGENTS.md and an import into CLAUDE.md. The hook owns only its own fence, and the hook fails open.No
Before a WriteValidates workflow artifacts: filename shape, required frontmatter, and a slug that matches the directory. The hook rejects a malformed artifact before the artifact touches disk.Yes
Before Write/Edit and BashThe optional leak guard: watches public docs, commit messages, and PR text for internal workflow references that cross the External Output Boundary. The guard is off by default, and it is advisory when on.No (advisory)
After a writeAuto-stages artifact writes in git; validates the structured sibling YAML that rich artifact types must ship; and hard-blocks a verify artifact that claims a pass while its own criteria are unmet.Yes (the verify result gate)
After a writeRender dispatch: enqueues the render job that the hub will drain.No

Notice the pattern: the hooks that block are exactly the hooks that guard the integrity of the record. They block an artifact that would be malformed, and they block a pass claim that the evidence contradicts. Everything else is background convenience that degrades gracefully. The full per-hook detail, including the config keys that tune each hook, lives in the hooks reference.

You can turn off or relocate every piece on this page. Per-repo settings live in .ai/sdlc-config.json, and machine-wide settings live in ~/.sdlc/hub-config.json. Environment variables, for example SDLC_DISABLE_BOOTSTRAP=1 and SDLC_DISABLE_TRAY_HEAL=1, disable individual pieces. The configuration reference describes each setting.
