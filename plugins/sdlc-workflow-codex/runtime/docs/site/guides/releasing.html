Releasing

This page walks the road from finished, reviewed code to a shipped release. Handoff packages the work into a PR, the ship plan defines how releases happen, ship executes one release, and retro closes the loop.

Handoff — from complete slices to a reviewable PR

When a slug's slices are implemented, verified, and review-clean, handoff turns the slices into something a reviewer can consume. Run handoff with the slug:

/wf handoff <slug>

By default, handoff aggregates all of the slug's complete slices into one package. It reads the whole artifact trail. It writes a reviewer-friendly summary (08-handoff.md) that covers the problem, the solution, verification evidence, risks, and follow-ups. It generates any documentation that the shape stage planned. It pushes the branch, and it creates or updates the pull request.

Then handoff waits. It watches CI to a terminal state, gives bot reviewers a bounded settle window, triages PR comments, and rebases the branch onto its base. After the wait, handoff computes a final readiness check from what actually landed: the CI conclusion, the review decision, GitHub's own merge state, and the triage outcome. Handoff is an orchestrator, not a fixer. When CI goes red, handoff dispatches a read-only diagnosis subagent, brings you the diagnosis, and asks how to proceed. It does not patch code itself.

The first argument is polymorphic. When you pass pr#N or a branch name instead of a slug, handoff switches to batch mode. Batch mode gathers every slug whose recorded branch matches into a roster. Each ready slug gets its own handoff package. One lead slug owns the single shared PR and the branch-level readiness check.

The roster report is printed before any packaging, and it answers the question "which slugs on this branch are handoff-ready". A slug that is not ready (missing reviews, an open blocker, a dont-ship verdict) is reported and skipped, and it does not block its siblings. The branch-level result is a logical AND across the roster: while the PR carries any slug's unreviewed commits, the PR is not ready.

One check is a hard block: the intent-risk ledger. If the workflow's control file still carries an intent-risk entry with status: open, handoff refuses. An unadjudicated entry means that shape never resolved a load-bearing ambiguity. To fix the entry, run /wf shape <slug>, so that the entry becomes adjudicated or consciously carried. Carried risks are legal, but they are surfaced in the PR body, so the reviewer sees them.

The ship plan — the project's release contract

Ship does not improvise a release. Ship executes .ai/ship-plan.md, a project-level document that records how this codebase ships. One plan exists per repository, and every workflow shares it. The plan records where the version lives, what secrets the pipeline needs, what a dry-run looks like, what to check after publishing, and what to do when things go wrong. Four sub-commands manage the plan:

/wf ship-plan init
Author the plan, once per repo. Templates seed sensible defaults for common shapes: kotlin-maven-central, npm-public, pypi, container-image, server-deploy, library-internal.
/wf ship-plan build
Bring the repo's actual pipeline into compliance with the plan: create missing files, and patch non-compliant files. The command supports --dry-run.
/wf ship-plan edit
Amend one block of the plan at a time. Every edit bumps the plan's version.
/wf ship-plan audit
A read-only soundness review of the plan, the built pipeline, and the release-relevant codebase. Findings accumulate in .ai/ship-plan-audit.md. Each finding is routed to the command that can fix it; the audit itself fixes nothing.

Both handoff and ship run the same readiness check against the plan before they proceed. A plan that no longer describes how the code ships lends false authority at exactly the moment when authority matters. The check detects a missing plan, and it detects drift: a version file that the plan no longer covers, a secret that a workflow uses but the plan does not list, or a new CI workflow that the plan predates.

Each drift finding is classified by what actually ends it. clears-on: amend means the plan is wrong about the repo, and an edit to the named block clears the finding. clears-on: repo means the repo is behind the plan. clears-on: merge means the finding is a true statement about the open branch, for example "this branch edits the release pipeline", and no plan edit can make the statement false before the branch lands. The gate only offers remedies that can actually clear the finding in front of you.

Findings that you consciously accept are recorded in an acknowledgement ledger, .ai/ship-plan-acks.yaml, so a settled question stays settled. An acknowledged finding is reported as one advisory line on later runs, and the gate does not ask about it again. Genuinely new drift always still gates. Acknowledgements are scoped: some die when the plan version bumps, and others live with the branch until the branch merges.

Ship — executing the release

When the PR is ready and the plan is current, run the release:

/wf ship <slug>

Ship refuses to start unless the handoff's readiness check came back ready. Ship also enforces two hard blocks of its own across every slug in scope: any open runtime-evidence deferral (a slice that passed verify only because runtime proof was deferred), and any open intent-risk entry. To clear a deferral, capture the evidence with /wf probe or with a re-verify in a capable environment, or record an explicit product-owner override. Ship never accepts a prose "we accept the risk" in the evidence field.

Each run gets a run-id, a compact UTC timestamp, and walks a 13-step sequence:

  • pre-flight: clean tree, version bump, secrets, changelog
  • publish dry-run
  • rollout questions
  • a freshness delta against the last successful run
  • an explicit go/no-go decision
  • merge
  • tag and release
  • a watch on the release workflow
  • a post-publish polling loop
  • the post-release version bump
  • index updates
  • the run artifact itself: 09-ship-run-<run-id>.md, indexed in 09-ship-runs.md

Every step is idempotent: the step detects its already-done state before it performs the side effect. A re-run of a completed step is a no-op with a note, never a duplicate merge or a second tag. Idempotent steps make the sequence replayable. When a run stalls, the run records status: awaiting-input with what blocked it. The next /wf ship <slug> offers to resume from the failed step instead of starting over. Questions that are answerable up front (scope, version, rollout strategy, release window) are batched into one round before the sequence opens, so an atomic run is never held open to wait for something that was knowable at minute zero.

Batch ship mirrors batch handoff. /wf ship pr#N ships every slug on the branch as one run, and the run is all-or-nothing: merge is atomic per PR, so either every slug on the branch is shippable or no slug ships. The lead slug owns the single run artifact, and each sibling's run index gets a pointer to it.

Two follow-up forms reuse a run without a second ship. Announce regenerates the release communications from the run artifact:

/wf ship <slug> announce

Rollback reverses a shipped run. It authors a reversal runbook and marks each step reversible or irreversible. It gates on its own go/no-go decision, executes the runbook, verifies the prior state, and writes 09-rollback-<run-id>.md:

/wf ship <slug> rollback [<run-id>]

Retro — closing the loop

The last stage extracts what the workflow taught. /wf retro <slug> reads the entire trail: every stage file, the review findings, the product-owner answers, and the design artifacts. It writes 10-retro.md: what went well, what hurt, root causes, and concrete, copy-paste-ready improvements to prompts, tests, repo instructions, and automation. Retro documents improvements; it never applies them.

The batch form, /wf retro pr#N, retrospects every slug on the branch, with one retro each. Then the batch form does the thing that no single-slug retro can do: it synthesizes the cross-slug lessons. Those lessons include friction that recurred across slugs, a shared root cause, and a plan assumption that broke the same way twice. The batch form distills the durable lessons into the repo's solutions corpus.
