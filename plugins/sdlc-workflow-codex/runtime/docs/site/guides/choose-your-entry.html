Choose your entry

This page tells you which single command starts the work in front of you. Read the page top to bottom once; after that, the situation headings are enough.

Everything enters through /wf, and almost everything enters through one key: /wf intake. Intake is the front door of the lifecycle, and intake has modes: alternative ways a piece of work comes in. You do not need to memorize the modes, because the plain form works everywhere. Describe the task, and intake either runs the default flow or proposes a better mode and asks before it switches. The situations below save you a round-trip. A few kinds of work (visual polish, runtime checks, cleanup triage) have their own keys.

You are building something new

This is the default entry. When you have a feature, an improvement, or any work with real scope, start the full lifecycle:

/wf intake add CSV export to the reports page

Default intake interviews you with product-owner questions, fingerprints the project's stack, and writes the workflow's index and intake brief. From there the nine remaining stages run in order: shape, slice, plan, implement, verify, review, handoff, ship, retro. Each stage is its own command, and each stage leaves an artifact behind. If you are new to the plugin, walk through this path once in Your first workflow before you try the other entries.

If your description begins with a word that intake treats as a mode keyword ("fix the typo…"), intake routes to that mode. That route is almost always the route you meant.

To force the default flow instead, quote the whole description as one token: /wf intake "fix is a strong word for this".

Something is broken

Three situations map to three modes. Pick by urgency and by how much you already know.

You can see the defect, and the correction is obvious. Examples are a wrong label, an off-by-one error, or a misaligned button:

/wf intake fix the export button label says "Exprot"

fix is a quick lane. It authors the whole planning half of the lifecycle in one run: brief, shape, slice, and plan. It works on a fix/<slug> branch, and it stops at a gate before implementation. No stage is skipped. The ceremony is compressed; the thinking is not.

Production is on fire. Examples are an outage, a live data problem, or users who are blocked right now:

/wf intake hotfix checkout returns 500 for all users

hotfix is the incident lane. It branches off the production branch. It diagnoses the root cause and the blast radius with parallel investigation. It locks scope hard: the only acceptable output is the minimum change that stops the incident. Review afterwards defaults to the security dimension.

Something broke, and you do not know why. When the cause is the question, do not start a fix mode. Diagnose first:

/wf intake rca the dashboard went blank after Tuesday's deploy

rca is terminal: it produces a root-cause analysis and a forwarding shape, then stops. It recommends where to go next. The usual routes are fix, hotfix, or a full intake, now supported by a diagnosis. The dividing line between fix and rca is this: run fix when the correction is self-evident and localized; run rca when you must find the cause first.

The code needs restructuring, not new behavior

/wf intake refactor untangle the auth service from the session store

refactor is the behavior-preserving lane. Before it touches anything, it captures a baseline: the public API surface, what the tests actually cover, and where the gaps are. It plans the work as atomic steps that each leave the build green. Identical external behavior is the only acceptance criterion, and review defaults to the refactor-safety dimension. The lane offers the dedicated refactor/<slug> branch; it does not force the branch.

Dependencies are due an update

/wf intake update-deps

update-deps scans every manifest and researches each outdated package against the package's own changelog. It sorts the work into risk tiers: security fixes first, then majors with migrations one at a time, then safe minor and patch updates as one batch. It is the one lane that also executes and verifies itself in the same run, so it goes straight to review afterwards. Pass a package name to focus on one dependency. Pass --security-only to update only CVE-affected packages. Pass --audit-only to get the plan and stop — the run closes as deferred, and the next run seeds from its Hold list. The details of all four quick lanes are in Quick lanes.

You have a question, not a task

Three analysis modes are available. All three are terminal: they end in an artifact and a recommendation, never in code:

/wf intake investigate <question>
Use this mode for an open design or approach question, for example "how should we…" or "what are the options for…". It produces option sketches with none pre-picked. You choose an option, then start the intake for the chosen approach.
/wf intake discover <question>
Use this mode for a yes/no truth question about the system, for example "does X actually…" or "is it feasible to…". It produces a feasibility verdict.
/wf intake ideate <area>
Use this mode for open-ended brainstorming with no specific defect or decision in view, for example "ideas for improving onboarding". It produces a ranked idea catalog. Each idea you pick seeds its own fresh intake.

The three modes are near neighbors. investigate sketches approaches to a stated problem. ideate hunts for problems worth having. discover answers one sharp question. When your description spans two of these modes, intake falls back to the default flow rather than guess. Investigation covers all three in depth.

The work is already done and sits uncommitted in your tree

/wf intake adopt

adopt is the reverse entry. Instead of planning work ahead of you, it reads the working-tree diff you already made and reconstructs the lifecycle behind the diff: brief, shape, slice, plan, and the implementation record. It then lands you at verify, where the standard chain takes over. It always roots a new workflow; it never attaches to an existing workflow. It records the branch you are on rather than create a branch. Intake never proposes adopt on its own; to adopt a diff is a decision you state.

You already have a workflow, and the new work belongs to it

Two forms exist, distinguished only by what follows the slug. There are no flags anywhere.

An existing slug plus a mode keyword attaches the run as a single quick-lane slice on that workflow:

/wf intake reports-export fix date column renders as epoch millis

The run creates no new workflow and no new branch. It adds one slice file to the workflow you named. This form fits the small defect or diagnosis you find mid-flight.

An existing slug plus free scope text is an extension. An extension grows the workflow with full new slices:

/wf intake reports-export also support XLSX output

Scope corrections and follow-on work land here. Already-built work is never re-specified in place; a correction is always a new slice. Two maintenance modes complete the set. /wf intake <slug> amend edits a workflow's recorded configuration (branch strategy, base branch, review scope, title, tags) against a strict whitelist. /wf intake <slug> modernize backfills an older workflow's artifacts to the current schema without a rewrite of any decision.

Intake resolves these forms in a fixed order, and the slug checks come first. A slug plus amend or modernize is maintenance. A slug plus a mode keyword is an attached slice. A slug plus anything else is an extension. A bare mode keyword is a standalone mode. Any other input runs default intake, which may suggest a mode and always asks before it switches. In practice: when you name an existing slug first, intake always acts on that workflow.

The work is visual

/wf design polish tighten the settings page hierarchy

UI and visual work has its own key. /wf design carries twenty commands. Fifteen are transformation verbs (polish, clarify, animate, layout, and more) that produce real code through a focused span. The rest are audit, critique, the read-only extract, and the setup/teach pair that authors your project's PRODUCT.md and DESIGN.md. See Design.

You want to check what actually runs

/wf probe <slug>

/wf probe drives the running artifact: the real app, not the code. It compares what it observes against the workflow's acceptance criteria. probe <slug> sweep widens the check to the whole user-facing surface, and a slug-less /wf probe sweep runs against any repo with no workflow at all. Probe reports findings; probe never writes code.

You want cleanup candidates, not cleanup

/wf simplify branch

/wf simplify sends three parallel reviewers over a scope you pick: a branch, a commit, a plan, or a directory of the codebase. The reviewers cover reuse, quality, and efficiency. The command classifies what the reviewers find and routes each finding to the correct downstream home. Like probe, simplify never fixes anything itself.

You want the stages driven for you

When a workflow exists, two drivers run the stages for you:

/wf auto <slug>
Human-gated: it drives stage after stage, pauses at each stage's own decision points, and stops before handoff.
/wf yolo <slug>
Autonomous: it resolves each gate by a written decision policy, records every decision it makes, and also stops before handoff. Handoff and ship always remain yours.

Autonomous drivers covers both.

If you remember one thing

When in doubt, type /wf intake followed by a plain description of what you want. The worst case is a one-question detour. The default flow handles everything the specialized entries handle, only with more ceremony. Run /wf status to see where you are and what to run next. When several workflows are open, run /wf status advise.
