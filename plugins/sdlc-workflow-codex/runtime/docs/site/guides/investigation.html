Investigation

Read this page when you need an answer, not a build: a diagnosis, an option map, a theory verdict, an idea catalog, a defect ledger, or runtime truth. Seven commands cover that ground, and none of them writes a line of application code.

The shared discipline: report and route

Every investigation command in the plugin follows the same rule: investigators report and route, they do not act. An RCA names a root cause but writes no patch. An option sketch characterizes tradeoffs but picks no winner. A probe records what the running product did but fixes nothing. A simplify run classifies findings and hands each finding a downstream command to run; it never executes the commands itself.

This separation is deliberate. Each investigation ends with an artifact and a recommendation. The fix, when there is one, goes through its own lifecycle with its own planning, verification, and review. That keeps the evidence trail honest: the diagnosis is never contaminated by pressure to make the fix look easy, and no code change slips through a side door that bypasses review.

Five of these commands are intake modes: rca, investigate, discover, ideate, and audit. The five modes are terminal: they end in an artifact and a routing decision rather than flow into a build. They create no branch. The other two commands, probe and simplify, are standalone keys with the same read-only posture. All seven can also attach to an existing workflow: pass a slug first, and the result lands as a quick-lane slice inside that workflow's directory instead of a new workflow.

rca — find out why it broke

When something is broken and you do not yet know why, start the diagnosis:

/wf intake rca checkout returns 500 after the discount migration

The command asks up to three questions: what is broken, what is the impact, and what changed recently. Then it launches parallel sub-agents that investigate the code path, correlate recent changes, and map the blast radius, including whether the same flawed pattern exists elsewhere in the codebase. The result is 01-rca.md: the root cause stated as a mechanism with cited file:line evidence, a confidence rating, contributing factors, and a "suggested fix shape". The suggested fix shape is deliberately a direction, not a plan: one to three lines that name the area and the approach, never enumerated steps.

rca is the one investigation mode that also writes a synthesized 02-shape.md, so the workflow directory is immediately consumable by planning. Its closing section recommends exactly one downstream route, and you record the route the same way an investigate pick is recorded — /wf intake rca <slug> <route> — before running the invocation it prints:

  • plan: the default for non-trivial fixes. The same slug continues into /wf plan <slug>, which reads the synthesized shape without modification.
  • fix: for a fix that fits in roughly three files with no architectural change. The rca closes and the printed invocation carries from <slug>, so the fix inherits the root cause, blast radius, and verification criteria instead of re-deriving them.
  • hotfix: for an active production incident where confidence is at least medium and the fix is small. Same closure and from <slug> forwarding.
  • Human triage: the last rung, not the first. Low confidence climbs a ladder first — a runtime probe on the slug, a source read of the implicated dependency, a second model via consult — and only low confidence that survives those rungs goes to a human.

Uncertainty is treated as data. If the sub-agents disagree, or if multiple plausible causes survive, the RCA records the disagreement rather than pick a tidy story. Tripwire warnings (low confidence, high blast radius, a concurrent PR that touches the same code) travel with the artifact, so the fix workflow inherits them.

investigate — sketch the options, pick none

investigate answers a different question: not "why is it broken" but "how could we solve this?" You give it a code-level problem, for example "checkout p99 latency is 2s" or "auth flow is brittle". It enumerates every genuinely distinct engineering approach grounded in the actual architecture, then characterizes each approach on effort, blast radius, reversibility, risk, and operational fit.

Three sub-agents run in two waves. An architecture cartographer and an option generator work in parallel; a tradeoff characterizer runs after both return and judges every option against the mapped constraints. Distinctness is enforced: "cache at layer X" versus "cache at layer Y" is one option, not two, and padding with near-duplicates is itself a flagged condition. Up to three options are presented as full cards. If more options survive, the surplus is recorded as compressed entries, and a tripwire tells you the option space was wider than the cards. The comparison table always leads with a status-quo column: the do-nothing baseline, with the cost of the unsolved problem as its top risk. Every option then reads relative to the choice to leave things alone.

Crucially, nothing is pre-picked. The artifact ends with a routing table, and you choose: a small option routes to /wf intake fix, and a medium or large option routes to /wf intake. If only one viable option exists, the command says so plainly rather than invent alternatives. If every option would violate the architecture, the command recommends a design pass instead of a choice among bad options.

Your pick becomes a recorded decision. Re-invoke the command with the slug and the option — /wf intake investigate <slug> B because it avoids the schema change — and the command stamps the chosen option and your reason into the artifact, then closes the workflow. The routed invocation carries from <slug>, so the successor workflow reads the investigation instead of re-deriving it: the chosen option's mechanism, risks, and architecture map seed its planning. If you route directly without recording a pick, the downstream mode records it for you and closes the investigation.

When no option clearly wins, each card names its decisive unknown: the one assumption that, if false, kills that option, and the cheapest way to check it. A truth question about the system routes to /wf intake <slug> discover, whose verdict attaches to the same workflow as a compressed slice. An API fact routes to the study-sources skill. A product call goes to the human who owns it. The stall becomes a named next action instead of a shrug.

discover — test a theory against the code

discover takes a falsifiable claim, for example "the rate-limiter is a token bucket in middleware/" or "feature A is implemented via Y", and adjudicates the claim. Three sub-agents argue the case: one builds the strongest evidence for the claim, one actively tries to falsify the claim, and one proposes counter-hypotheses that fit the same observable behavior. The verdict is convergent, exactly one of holds, partial, fails, or inconclusive, with confidence and cited evidence on both sides.

A partial verdict states precisely which part of the claim holds and which part fails. That is often the most useful outcome: a refined hypothesis you can carry forward. inconclusive is also a legitimate answer. When static code reading cannot settle the claim, the artifact lists exactly which runtime signal would settle it (a test run, a profile, a log line) rather than guess. A failed hypothesis about a bad behavior routes to rca with from <slug> — the counter-hypotheses the third sub-agent ranked are candidate root causes, and the forwarding hands them to the rca's investigators. A confirmed hypothesis requires nothing further; proceed with whatever you intended. Either way the discover workflow closes the moment its verdict is written — a verdict leaves nothing to pick — and the artifact records which decision rode on it, so a fails names the plan that just lost its premise.

ideate — find out what is worth doing next

ideate inverts the usual pattern: instead of a problem you bring, it scans the codebase for problems you did not think to ask about. Six lenses run in parallel: code quality and technical debt, performance and scalability, security and privacy, developer experience, feature completeness, and architecture. The lenses generate thirty or more raw candidates, each grounded in specific file:line evidence.

Then comes the adversarial filter, which is mandatory. Every candidate must survive five challenges: is it real, is it already in progress, is the effort justified, is it specific enough to act on right now, and is it a root cause or just a symptom? Culled ideas are recorded with reasons. Survivors are scored by impact and effort and presented as a ranked catalog, and the catalog is the point of the whole exercise: each surviving idea maps directly to a /wf intake command. ideate does not start any of them. It hands you a menu; your selection is persisted on the artifact, and a recorded pick (/wf intake ideate <slug> <idea-id>) closes the workflow and prints the successor invocation, seeded with the idea's evidence via from <slug>. To narrow the scan, add a focus area and a count:

/wf intake ideate security 5

audit — hunt the defects nobody has named yet

audit fills the gap the other four modes leave open. rca needs a symptom; discover needs a hypothesis; investigate needs a decided problem; the review stage needs a diff. When the request is "scrutinize this subsystem for bugs, wrong assumptions, and mistakes" — and nobody can yet name one — that is an audit:

/wf intake audit the paint-ordering code, GPU and CPU paths

The run starts by resolving the concern to a concrete file surface, because a subsystem is not a path. Parallel sub-agents enumerate candidates by four different search modalities (entry points, call graph, naming, test coverage), the union is presented to you for confirmation before any lens runs, and exclusions are recorded with reasons. That confirmation is the legibility requirement: an audit whose scope was silently guessed cannot be trusted when it reports "no findings", because the reader cannot tell clean from unread.

The lenses are review's own rubrics — audit owns none of its own — and the selection is stated with a one-line reason per lens. Every candidate finding then faces adversarial refutation before it lands: refuters are prompted to kill the finding, a BLOCKER or HIGH gets three refuters with distinct angles, and refuted candidates are kept with their refutations rather than silently dropped. Survivors merge into the same accumulating findings ledger the review stage owns: a re-run preserves prior IDs, marks cleared findings resolved, and never overwrites — so a multi-session audit never re-surfaces the same twelve findings from scratch, and you can always tell what was deliberately deferred from what was never seen.

Some findings cannot be settled by reading — most sharply, "these two paths disagree at runtime". Those are recorded at low confidence as needs-runtime-evidence with the exact experiment named, and they route to /wf probe. Everything else routes too: a mechanical defect to fix, an unexplained symptom to rca, a restructuring question to investigate, and a non-code outcome (rotate the leaked key, file the upstream issue) to /wf task. audit fixes nothing, ever. A zero-finding run is a valid result, written legibly enough that the next audit knows what was covered.

probe — drive the running product against its promises

Everything above reads code. probe is the runtime counterpart: it boots and drives the actual running artifact. It clicks, taps, sends requests, and invokes the CLI. It captures observable evidence (screenshots, stdout, response bodies) and compares what it saw against what was promised. probe is to rca what runtime is to static analysis: rca reads code and history; probe runs the product and watches.

probe operates on an existing workflow. When you give probe a target, it fuzzy-matches the target against the workflow's acceptance criteria, slices, and surfaces. When you give probe nothing, it probes every acceptance criterion in the workflow:

/wf probe <slug> checkout applies the discount before tax
/wf probe <slug>

Findings land as a quick-lane slice, 03-slice-probe-<descriptor>.md, with evidence files alongside. A probe can also clear a recorded runtime-evidence deferral, the IOU a workflow carries when verification could not produce runtime proof, when the probe's observation satisfies the deferred criterion. If the environment does not even boot, probe records that failure too, as an awaiting-environment slice with the failing step and a remediation hint. The gap is then visible rather than silent.

Sweep mode and the surface-defect taxonomy

sweep is a reserved word that widens the comparison basis. /wf probe <slug> sweep enumerates the whole user surface and checks it against three things at once: every acceptance criterion, every charter constraint, and a shared taxonomy of eight defect classes. A charter constraint is a durable, cross-slice promise the product owner ratified; criteria expire per slice, the charter does not. Each defect class carries a detection question, and the probe asks that question of every enumerated surface:

ClassThe question it asks
dead-affordanceIs there an interactive control whose handler does nothing?
error-surface-leakIs any upstream or internal error rendered as user-facing content?
terminal-waitCan this loading state be entered and never left?
fabricated-valueIs any displayed figure derived from a constant or placeholder rather than data?
dependency-collapseDoes one unavailable source take down surface that does not depend on it?
branch-gapIs a guarantee present only in the happy branch?
boundary-overflowDoes layout or output exceed the real target dimension?
env-interferenceCould ambient state — not the artifact — have produced what was observed?

A sweep's report leads with the coverage claim, not the finding count: how many surfaces were enumerated, how many were driven, and which were unreached and why. "I found no bugs" is not a result. "I enumerated six surfaces, drove six, and here are the two I could not reach" is a result. Where authorized, a sweep also perturbs: it deliberately breaks one dependency, re-observes, and restores the dependency. Perturbation is the only way to find dependency-collapse and branch-gap on purpose rather than by luck. Any non-trivial finding from a single observation must be re-observed from a clean state before it is recorded, precisely because of env-interference.

The sweep also runs without a slug: /wf probe sweep [path] needs no workflow at all. With no acceptance criteria and no charter to compare against, the taxonomy alone is the basis, and the report lands at the project level as .ai/surface-sweep-<utc-date>.md. The slug-less sweep is the cheapest way to point the eight questions at any repo you just inherited.

In every mode, probe may start dev servers, boot emulators, and build and install; bootstrap is authorized. probe may never edit a source file. probe observes; downstream commands fix.

simplify — three reviewers, findings routed, nothing fixed

simplify is triage for code quality. It dispatches three reviewers in parallel. Reuse asks whether new code duplicates an existing helper. Quality looks for redundant state, copy-paste variation, leaky abstractions, and stringly-typed code. Efficiency looks for redundant work, missed concurrency, hot-path bloat, and memory leaks. The reviewers run across one of four scopes:

/wf simplify                      # the current branch's diff (default)
/wf simplify commit <sha>         # one commit or a range
/wf simplify plan <slug> <slice>  # a plan's prose, not a diff
/wf simplify codebase [path]      # a whole subtree

Independently of the reviewers, simplify harvests sdlc-debt: markers, the shortcuts that implementation flagged with a ceiling and an upgrade path, and folds them in as pre-classified findings. Markers exist for routing, not rediscovery. simplify's codebase scope is the repo-wide sweep of that declared debt backlog.

You triage each finding: accept, skip, or defer. Every accepted finding gets a route from a fixed matrix:

  • A one-file mechanical cleanup routes to /wf intake fix.
  • A behavior-preserving multi-file restructure routes to /wf intake refactor.
  • Anything with behavior or architectural impact routes to a full /wf intake.
  • Missing tests route to a verify or an add-a-test fix.
  • Plan problems route to a directed plan correction.

The rule is always the smallest scope that fully addresses the finding; never escalate beyond what the finding deserves. simplify then prints the invocations and stops. It does not write code, not even the trivial typo it just flagged. The moment a triage tool starts to fix things, it becomes a back-door write path that bypasses planning, verification, and review.

Which one do I want?

/wf intake rca
Something is broken, and you need to know why. rca starts from a symptom.
/wf intake investigate
You know the problem and need to see the solution space. investigate starts from a problem; you pick the approach.
/wf intake discover
You have a theory about the code and need a verdict. discover starts from a falsifiable claim.
/wf intake ideate
You do not have a question yet; you want to know what is worth doing. ideate starts from nothing.
/wf probe
You need to know what the running product actually does, versus what was promised.
/wf simplify
You want the code reviewed for reuse, quality, and efficiency, with each finding sent to the correct fix lane.
